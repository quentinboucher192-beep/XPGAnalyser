# Les sessions : travailler à plusieurs sur le même projet (1.43.0, réseau du bureau ; 1.44.0, par Internet ; 1.45.0, retirer, partir, le journal)

La maquette validée est `docs/maquettes/1.42.0/` (planches 07 à 11). Ce document dit comment c'est fait : `src/session/` (le protocole, le lien, les changements ; sans écran, `session_test`) et `src/app/SessionService`, `SessionDialogs`, `SessionMarks` (IHM Studio).

## 1. Ce que fait la 1.43.0 (et ce qui vient après)

- **IHM Studio, sur le réseau du bureau.** Un PC **démarre** une session sur le projet ouvert (il en est l'**hôte** : son PC garde le projet et l'enregistre) ; les autres la **rejoignent** : au bureau, elle apparaît seule dans « Rejoindre » ; l'hôte accepte chaque entrée, ou exige le code de la session.
- Le projet arrive une fois chez l'équipier (dans un dossier de session, à part de ses projets), puis **seulement les changements**, objet par objet.
- **Chacun voit ses équipiers** : leurs pastilles en haut, la vue où ils sont, les objets qu'ils ont **réservés** (contour à leur couleur, leur nom) ; « Suivre » ouvre la vue d'un équipier ; une discussion.
- **Chacun son objet** : un objet choisi par un équipier est réservé pour lui tant qu'il le garde choisi ; les autres ne peuvent pas le choisir (ils voient par qui il est pris).
- **Ctrl+Z annule ses propres gestes**, pas ceux des autres. **L'hôte enregistre** pour tout le monde ; **l'historique des objets** signe chaque objet par le PC de celui qui l'a modifié (son nom, son identifiant stable « M-7F21 », la session).
- **1.44.0 : par Internet** (§ 7) : la même session à travers le relais du service XPG (le service des licences), chiffrée de bout en bout ; le code de 10 caractères (« K7Q4-M2XP-T9 ») suffit pour entrer.
- **1.45.0** (§ 8) : l'hôte **retire** un équipier ; qui **part** revient à l'accueil (l'hôte qui arrête coupe tout le monde) ; **l'équipier ne garde rien** (sa copie est effacée) ; l'onglet **« Session »** du panneau du bas, les membres dans l'arbre du projet et dans l'explorateur d'objets ; le **journal** de la session (qui a changé quoi, quand).
- **Plus tard** : API Studio en session (ses commandes d'édition annulent par troncature : à reprendre d'abord), « Regarder seulement » changé en direct, la reprise après une coupure longue.

## 2. La licence

- **Démarrer** une session demande la fonctionnalité `multi_user` (« Travail à plusieurs ») : l'offre ENTERPRISE, ou l'option « Travail à plusieurs ».
- **Rejoindre** demande seulement sa propre licence d'IHM Studio.

## 3. Le réseau

| | |
|---|---|
| Découverte | UDP **47864**, en diffusion sur le réseau du bureau (`{"xpgs":1,"op":"CHERCHE","nonce":…}` → `{"xpgs":1,"op":"ICI",…}` : le nom de la session, l'hôte, son PC, le logiciel, le projet, le port, l'empreinte de son certificat, le nombre de membres, si un code est demandé). Ports à part de ceux du déploiement (47861, 47862) : un agent sur le même PC ne gêne pas. |
| Le lien | TCP **47863**, **TLS 1.3** (la bibliothèque du déploiement réseau : mbedTLS), les deux côtés présentent leur certificat (le certificat du Studio, `Deploiement/studio.cer`, créé une fois sur chaque PC). L'équipier épingle l'empreinte annoncée par l'hôte ; l'hôte voit celle de l'équipier (son identifiant « M-7F21 », dans la fenêtre « Léa veut entrer »). |
| Le code | Avec « Il faut le code » : 6 chiffres (montrés « 482 913 »), nouveaux à chaque session ; **jamais transmis**, même haché : un échange CPace (celui de l'appairage du déploiement, lié aux deux empreintes TLS) prouve que les deux le connaissent. L'échange est aussi lié à la session (SHA-256 de « XPG-SESSION-v1\|identifiant ») : un code de session ne sert ni à un appairage de déploiement, ni à une autre session. Un intermédiaire qui présente ses propres certificats fait échouer l'échange sans rien apprendre du code. 3 essais par équipier (son empreinte) : l'essai compte dès que l'hôte répond. |
| Les trames | Celles du déploiement : longueur, en-tête JSON, données ; 2 Mio au plus (le projet part en morceaux de 1 Mio). |

## 4. Les messages

| De → à | `op` | Ce qu'il porte |
|---|---|---|
| équipier → hôte | `BONJOUR` | son nom (Mon profil), son PC, son identifiant, son logiciel et sa version, l'identifiant de la session ; avec un code : `CODE_DEMANDE`, puis l'échange CPace (`CODE_DEBUT` / `CODE_REPONSE` / `CODE_FIN`) |
| hôte → équipier | `LIEN_OK` | la poignée de main est faite (le code prouvé s'il le fallait) : l'hôte décide maintenant |
| hôte → équipier | `ATTENTE`, `ENTREE`, `REFUS` | en attente de l'hôte ; accepté (son numéro de membre, sa couleur, son rôle, son bloc d'identifiants, les membres) ; refusé (la raison) |
| hôte → équipier | `PROJET` ×n, `PROJET_FIN` | les fichiers du projet (`ihm/…`), en morceaux |
| les deux | `VUE` | les changements d'une vue : ses objets changés (leur texte, comme dans le fichier de la vue), ceux supprimés, l'ordre de dessin, la vue elle-même si ses propriétés ont changé |
| les deux | `FICHIER` | un fichier du projet hors des vues (les variables, les scripts, les réglages…), entier |
| les deux | `PRESENCE` | la vue où il est, ses objets choisis |
| équipier → hôte | `RESERVE` | les objets qu'il choisit ; l'hôte répond par `RESERVATIONS` (qui tient quoi, pour tous) |
| les deux | `MESSAGE` | la discussion (`de`, `couleur`, `texte`, `heure`) ; 1.50.0 : `id` (donné par l'hôte, le même pour tous) et `reponse` {`id`, `de`, `extrait`} (le message auquel il répond, son auteur, le début de son texte), **facultatifs** : un Studio plus ancien les ignore et lit le texte. L'hôte envoie à un Studio d'avant la 1.50 la réponse avec la citation en première ligne du texte (« En réponse à Léa : « … » ») ; un équipier 1.50 chez un hôte plus ancien fait de même (l'hôte ne garderait pas `reponse`). Un message sans `id` (un hôte d'avant) reçoit un identifiant tiré de son auteur, son heure et son texte : le même sur chaque PC |
| hôte → tous | `MEMBRES` | qui est là, où, avec quel rôle |
| les deux | `AUREVOIR` | il part ; l'hôte arrête : la session se ferme pour tous (`fin`, `raison` : « Camille a arrêté la session ») ; 1.45.0 : l'hôte retire un équipier (`retire`, `raison` : « Camille t'a retiré de la session ») |
| hôte → tous | `NOUVELLE` | 1.45.0 : une nouvelle de la session (`texte`, `couleur`, `ton`) : « Léa a quitté la session », « Camille a retiré Léa de la session » - la discussion, la barre d'état, une notification |
| hôte → tous | `JOURNAL` | 1.45.0 : le journal de la session (`entrees` : numéro, heure, membre, auteur, couleur, texte, gestes fondus) ; `tout` : le journal entier (envoyé à l'entrée, juste après `ENTREE`) ; sinon les entrées neuves ou fondues (le même numéro remplace) |
| hôte → équipier | `REFUSE_CHANGEMENT` | un changement refusé (l'objet est pris, il regarde seulement) ; l'état juste est reparti avant (`VUE` ou `FICHIERS`) |
| hôte → tous | `ETAT` | toutes les 4 s, quand le projet a changé : l'empreinte (SHA-256) de chaque vue et de chaque fichier hors des vues |
| équipier → hôte | `RESYNC` | au calme (rien à envoyer, rien reçu depuis un moment), ce qui diffère de `ETAT` : l'hôte renvoie la vue entière ou le fichier (3 fois au plus par élément : un écart qui ne se rattrape pas ne boucle pas) |

**L'hôte fait foi** : un changement d'un équipier lui arrive d'abord ; il le refuse s'il touche un objet réservé par un autre (ou si l'équipier ne peut que regarder) et renvoie alors l'état juste ; sinon il l'applique et le renvoie à tous, dans l'ordre. Chacun applique les changements des autres **objet par objet** : deux équipiers sur deux objets de la même vue ne s'écrasent pas.

**Les identifiants** : chaque membre crée ses objets (et ses vues, ses variables…) dans **son bloc** d'identifiants (le membre n, à partir de n × 2^28 ; une session d'avant a pu y laisser des objets : le premier libre) : deux objets créés en même temps sur deux PC n'ont jamais le même. Le compteur reste à chacun : il ne passe pas dans les fichiers.

**Le reste du projet** (`ihm.txt`, les scripts, les ressources…) passe en **différences de lignes avec leur contexte** : deux équipiers qui ajoutent chacun une variable ne s'écrasent pas. Deux ajouts au même endroit peuvent se ranger dans un ordre différent chez l'un et l'autre : les empreintes le voient, l'équipier reprend le fichier de l'hôte. Une vue neuve passe entière avec l'index qui la cite ; une vue retirée par un équipier part dans la corbeille de l'hôte.

## 5. Ce qui reste local

- La pile d'annulation : Ctrl+Z annule ses gestes (le changement part aux autres comme un geste de plus). En session (`hmi::Document::shared`), annuler ne remet que les objets que le geste a touchés, par-dessus l'état courant : ce qu'un équipier a fait depuis reste ; le reste du projet est reporté ligne par ligne (`session::mergeShell`).
- L'enregistrement : seul l'hôte enregistre le projet. 1.45.0 : **l'équipier ne garde rien** (§ 8) - sa copie est effacée quand il part ; il n'en fait pas d'autre pendant la session.
- La simulation, les essais, le poste d'exploitation : chacun les siens.

## 6. Dans IHM Studio

- **Projet › Démarrer une session…** : le nom ; **Où** (1.44.0) : « Réseau du bureau » ou « Internet (par le service XPG, chiffré de bout en bout) » ; qui peut entrer (réseau du bureau : j'accepte chaque entrée / il faut le code ; par Internet : il faut le code, montré dans la fenêtre avec « Copier » avant de démarrer) ; ce qu'ils font en entrant (modifient / regardent seulement). Le projet est enregistré avant ; un projet verrouillé (LOCK) ne se partage pas. La licence : `multi_user` (la table des points d'entrée : l'action fermée propose l'option).
- **Projet › Rejoindre une session…** (et le lien de l'accueil, sans projet ouvert) : deux choix en toutes lettres en tête (1.44.0). **« Sur le réseau du bureau »** : les sessions trouvées seules (celles du réseau et de ce PC), « Actualiser » ; on en choisit une, « Rejoindre » ; le champ du code n'apparaît **que** si la session choisie le demande ; « Une autre adresse… » (le nom ou l'IP du PC de l'hôte, pour un autre réseau ou un VPN) est replié. **« Par Internet »** : un seul champ, « Le code de la session (donné par l'hôte) ». (La 1.43 montrait toujours l'adresse et le code dans un formulaire : on croyait devoir les remplir.) Le projet arrive dans `<dossier commun>/Sessions/<identifiant>` (pas dans les projets récents).
- **La pastille « Session · 3 »** en haut (à côté de la licence ; orange quand quelqu'un frappe) : l'équipe (où chacun est, combien d'objets il tient, Suivre, Regarder seulement / Laisser modifier pour l'hôte), ceux qui veulent entrer (Faire entrer / Refuser), le code (« Code de la session : K7Q4-M2XP-T9 » par Internet, Copier le code), la discussion, Arrêter / Quitter.
- **Les objets tenus** : un contour à la couleur de l'équipier et son nom au-dessus ; un objet tenu ne se choisit pas (la barre d'état dit par qui il est pris).
- **Enregistrer** : l'hôte ; chez l'équipier, Ctrl+S envoie tout de suite ce qui attend à l'hôte et le rappelle. 1.45.0 : à la fin, l'équipier revient à l'accueil et sa copie est effacée (§ 8).
- **La discussion** (1.50.0, l'onglet « Session » et la fenêtre de la session : la même liste) : **Répondre** à un message (le survol : deux pictogrammes en haut à droite ; le clic droit) montre « En réponse à Léa : « début du message… » » au-dessus du champ (✕ ou Échap l'annule) ; la réponse montre l'extrait cité au-dessus de son texte, un clic dessus met le message cité en vue et le choisit. **Réduire / Déballer** : un message de plus de cinq lignes (à la largeur du moment) montre ses quatre premières lignes puis « … voir tout » ; déballé, « Réduire » ; le clic droit : Déballer / Réduire, « Tout réduire ». **Copier** (le survol, le clic droit, Ctrl+C sur le message choisi) : le texte seul ; « Copier avec l'auteur et l'heure » : « 14:32 Léa Essai : bonjour ». Tout reste dans son cadre à toute taille (`session_ui_test`).
- **Les essais** : `session_test` (le protocole, le miroir, Ctrl+Z en session, un vrai lien TLS sur la boucle locale) ; `session_relay_test` (ctest `sessionrelais`, 1.44.0 : par Internet, § 7) ; les commandes de script `session-*` ; l'essai de bout en bout sous Wine (deux IHM Studio, une licence ENTERPRISE d'essai). `XPG_DOSSIER_COMMUN` impose le dossier commun (deux Studios côte à côte, chacun le sien).

## 7. Par Internet (1.44.0)

Pour un équipier à distance, la session passe par le **relais du service XPG** : le service des licences que le Studio connaît déjà (son adresse compilée ; dans une construction d'essai, `XPG_SERVICE`), un Durable Object par session (`service/src/relais.js`, le contrat : `docs/SERVICE-LICENCES.md`, § 5 bis). Le relais ne fait que **passer des octets chiffrés de bout en bout** : ni le code, ni le projet, ni les noms des équipiers, ni la discussion n'y passent en clair. C'est `session/SessionRelay` (`RelayHostLink`, `RelayGuestLink` : les mêmes événements et les mêmes appels que `HostLink` / `GuestLink`) et `app/SessionRelayHttp` (le HTTP signé).

| | |
|---|---|
| Le code | **10 caractères** du base32 de Crockford (50 bits), montrés « K7Q4-M2XP-T9 », tirés à chaque session ; tapés avec souplesse (minuscules, espaces, tirets ; O pour 0, I et L pour 1). L'entrée est toujours « il faut le code » : le code prouvé, l'hôte fait entrer. |
| Le localisateur | **Argon2id** du code (libsodium `crypto_pwhash` : 3 passes, 64 Mio, un sel fixe tiré de « XPG-RELAIS-v1 »), 16 octets en hexadécimal : c'est ainsi que le relais connaît la session. Lent exprès (0,2 à 0,7 s, calculé dans le fil du lien, une fois par démarrage ou par entrée) : **le service ne peut pas retrouver le code en essayant toutes les combinaisons**. **Un code faux ne trouve aucune session** (404 : « aucune session ouverte avec ce code »). |
| Les appels | signés par la clé de chaque PC (`X-XPG-*`, comme les autres appels au service : la clé de ce PC, `licensing::deviceSignServiceMessage`) ; l'heure signée : celle du service (`GET /v1/etat`). Deux fils par lien, jamais celui de l'interface : l'un lit en **attente longue** (25 s), l'autre envoie (les trames en attente regroupées : 1,4 Mio au plus par appel ; l'hôte écrit à plusieurs équipiers d'un appel, chacun son tour en tête). |
| L'entrée | l'échange **CPace** des appairages (`deploy::pairing` : ristretto255), le **code** pour secret, lié au localisateur et à la connexion donnée par le relais : G = ristretto255_from_hash(SHA-512(« XPG-RELAIS-v1 » ‖ code ‖ sid ‖ canal)), canal = SHA-256(« XPG-RELAIS-CANAL\|localisateur\|connexion »). L'équipier envoie `CODE_DEBUT` {sid, Y}, l'hôte répond `CODE_REPONSE` {Y, sa confirmation, les essais qui restent}, l'équipier vérifie l'hôte puis envoie `CODE_FIN` {sa confirmation} (en clair : ce sont des valeurs publiques de l'échange). Un relais hostile (ou une collision de localisateurs) qui mène un code faux jusqu'à l'hôte : l'échange échoue des deux côtés, **3 essais par clé de PC** (comme sur le réseau du bureau), puis refusé même avec le bon. |
| Le chiffrement | une clé par sens (BLAKE2b de la clé de l'échange) ; chaque trame du protocole (§ 4 : `BONJOUR`, `LIEN_OK`, puis `ATTENTE`, `ENTREE`, `PROJET`…) est **scellée** (XChaCha20-Poly1305, libsodium) : un compteur par sens dans le nonce, le localisateur, la connexion et le sens dans les données associées. Un message rejoué (ou un envoi refait) est ignoré ; un message modifié, perdu ou dans le désordre ferme la connexion. Une trame de plus de 1 Mio part en morceaux (32 Mio au plus). Le `BONJOUR` (le nom, le PC) part scellé. Sur le relais, un envoi est une suite d'enregistrements ([longueur][`C` + JSON en clair \| `S` + compteur + texte scellé]). |
| Les départs | l'équipier qui part, l'hôte qui arrête, un PC qui ne lit plus (90 s ; l'hôte : 120 s) : le relais le dit (une « fin ») ; le lien le rend comme une connexion fermée. Plus de réponse du relais pendant 2 min : la session s'arrête. |
| Les limites | celles du relais (`docs/SERVICE-LICENCES.md`, § 5 bis) : 8 membres, 1,5 Mio par appel, 16 Mio en attente par boîte (le projet qui part attend que l'équipier lise), 12 h sans activité. |

**Ce qui reste comme au bureau** : tout le reste (le projet qui arrive, les changements objet par objet, les réservations, la discussion, l'hôte qui fait foi, l'enregistrement chez l'hôte). La session par Internet n'est pas annoncée sur le réseau du bureau.

**Les commandes de script** (l'essai de bout en bout) : `session-demarrer "Nom" internet [modifier|regarder]` (attend que la session soit ouverte sur le relais, puis écrit le code, « K7Q4-M2XP-T9 », dans `code-session.txt` du dossier des captures), `session-attendre ouverte` (l'hôte : ouverte sur le relais), `session-rejoindre internet @fichier` (le code de `code-session.txt` ; ou `@<chemin>`, ou le code lui-même). Le relais : celui du service des licences du Studio (`XPG_SERVICE` dans une construction d'essai : le service local, `outils/service/lancer-local.sh`). Les commandes du réseau du bureau restent les mêmes.

## 8. Retirer, partir, le journal (1.45.0)

Le client : « pouvoir virer qlq dans une session », « quand quelqu'un quitte la session si c'était pas l'hôte ça le ramène à la page d'accueil et ça envoie une notif aux autres, si c'est l'hôte ça coupe tout le monde », « qlq qui a rejoint une session, quand elle part les données de l'appli ne sont pas sauvegardées sur son pc », « où se situe l'historique dans les sessions des choses modifiées par tout le monde ». Pareil sur le réseau du bureau et par Internet.

| | |
|---|---|
| **Retirer** | Dans la fenêtre de la session, chaque équipier a « Retirer de la session… » (l'hôte ; une question d'abord). L'équipier est coupé avec sa raison (`AUREVOIR` `retire` : « Camille t'a retiré de la session »), revient à son accueil, sa copie s'efface ; les autres le lisent (`NOUVELLE` : « Camille a retiré Léa de la session », dans la discussion et une notification). **Son PC est retenu** (l'empreinte de son certificat ; par Internet, la clé de son PC) : s'il frappe de nouveau, il n'entre pas seul, même avec le code - l'hôte le voit (« Léa (retiré tout à l'heure) veut revenir ») et décide ; le faire entrer le pardonne. |
| **Un équipier part** | Quitter, fermer le projet, fermer l'appli, le lien perdu : il revient à l'**accueil** ; les autres : « Léa a quitté la session » (la discussion, la barre d'état, la cloche). |
| **L'hôte arrête** | Le bouton, fermer le projet, fermer l'appli : tous les équipiers sont coupés et reviennent à l'accueil (« Camille a arrêté la session », une notification) ; l'hôte reste sur son projet. |
| **L'équipier ne garde rien** | Le projet reçu arrive dans `<dossier commun>/Sessions/<identifiant>` (jamais dans les projets récents, pas de sauvegarde de reprise). Quand l'équipier part, pour toute raison, la copie est **fermée et effacée** ; ce qu'un arrêt brutal a laissé est effacé au lancement suivant (sauf une copie ouverte dans une autre fenêtre). Pendant la session : Enregistrer sous, Dupliquer, Exporter en archive, Vers Control Expert, le dossier du projet dans l'explorateur (le menu de l'arbre, « Ouvrir dans l'explorateur » d'un chemin du projet), l'export ou l'extraction d'une version : **refusés**, grisés avec la raison « En session, le projet reste chez l'hôte » (`sessionmarks::keepRefusal`). Ctrl+S envoie à l'hôte. |
| **L'onglet « Session »** | Dans le panneau du bas d'IHM Studio, à côté de Sorties, Console, Diagnostics, Performances : il **n'existe que pendant une session**. La discussion et le journal mêlés dans l'ordre des heures, ou filtrés (Tout, Discussion, Journal) ; sa pastille : les messages des autres pas encore lus ; le champ du bas écrit à l'équipe (Entrée) ; l'hôte : « Exporter le journal (CSV) ». |
| **Les gens dans les explorateurs** | En tête de l'arbre du projet, le nœud « Session » : chaque membre, ses initiales dans sa couleur, son nom, hôte ou équipier, son PC, la vue où il est, Modifier ou Regarder ; un clic le suit (sa vue s'ouvre). Dans l'explorateur d'objets de l'éditeur de vues, un objet tenu par un équipier porte ses initiales dans sa couleur (l'infobulle : « tenu par Léa »). |
| **Le journal** | Chaque changement appliqué pendant la session, en une phrase signée : « 14:32 Léa : Vue_Accueil › Texte_Etat déplacé », « 14:35 Camille : ressource logo.png ajoutée », « variable Debit ajoutée », « script Init modifié », « vue Vue_2 ajoutée » (`session/SessionJournal` : les objets ajoutés, déplacés, redimensionnés, renommés, modifiés avec leurs propriétés, supprimés ; plus de 3 objets d'un geste : « 12 objets déplacés » ; les propriétés de la vue ; le reste du projet lu dans l'index `ihm.txt` et ses fichiers). **L'hôte le tient** (tout passe par lui) et l'envoie à tous (`JOURNAL`) ; un équipier qui entre tard le reçoit entier. Borné à 2 000 entrées (les plus anciennes tombent) ; un geste répété (un glisser) se fond dans l'entrée récente du même auteur et du même texte (moins de 2 min) : « (×12) ». Il se lit dans l'onglet « Session » et dans la fenêtre de la session (« Journal »). L'hôte l'exporte (`exports/journal-<date>_<nom>.csv`) et, **à la fin de la session, il est enregistré avec le projet** : `<projet>/ihm/historique/sessions/AAAA-MM-JJ_HHhMM_<nom de la session>.csv` (point-virgule, UTF-8 avec sa marque : Date, Heure, Auteur, Changement, Gestes). À côté de l'historique des objets (1.43, signé par le PC de l'auteur) : celui-ci dit tout ce qui s'est passé, par tout le monde, dans l'ordre. |
| **Les ressources** | Une ressource (une image) ajoutée par un équipier passe entière (`ressources/…`) : elle arrive chez l'hôte puis chez les autres, et s'inscrit au journal (« ressource logo.png ajoutée ») ; `session_test` le vérifie. |
| **Un service trop vieux** | Un service des licences d'avant la 1.44 ne connaît pas le relais (404 « route » sur `/v1/relais/ouvrir` ou `/v1/relais/<localisateur>/frapper`) : le Studio dit « Le service des licences n'est pas encore en 1.44 : l'éditeur doit le redéployer (Admin › Service en ligne › Déployer). » (au lieu de « cette adresse n'existe pas sur le service des licences »), en démarrant comme en rejoignant. |

**Les commandes de script** (l'essai de bout en bout) : `session-retirer N` (l'hôte retire le membre N : « [script] session-retirer 1 : Léa retiré(e) »), `session-quitter` (l'équipier part), `session-attendre accueil` (revenu à l'accueil, la copie fermée et effacée : « [script] session-attendre accueil : oui (copie effacée : <dossier>) »), `session-attendre journal "texte"` (une ligne du journal le contient), `session-journal` (« [script] session-journal : N entrée(s) » puis une ligne par entrée ; l'hôte, à la fin : le fichier enregistré), `session-onglet` (l'onglet « Session » du panneau du bas : « [script] session-onglet : N ligne(s) · M message(s) · K au journal ») ; `session-attendre fin` reste.

**Les essais** : `session_test` (le journal : un objet déplacé, ajouté, modifié, supprimé, une ressource d'un équipier qui arrive chez l'hôte et les autres, une variable, la fusion, la borne, le CSV enregistré ; la copie effacée au départ et purgée au lancement ; de vrais liens : retirer, partir, arrêter ; le service trop vieux), `hmi_editor_test` (l'onglet « Session » n'existe que pendant une session, son non lu, écrire ; le nœud « Session » de l'arbre ; « tenu par Léa » ; les refus de l'équipier).
