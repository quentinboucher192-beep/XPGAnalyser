Neuf concepts pour le langage des scripts

Les vues, les objets, les symboles d'IHM Studio sont riches ; le langage des scripts, lui, avait des manques. La 1.13.0 les comble (sauf les grafcets, qui restent cote automate).

Une precision. Les echanges reseau depuis un script (HTTP, MQTT, SQL) ne sont pas dans ce lot : sortir une connexion reseau d'un script touche au meme garde-fou de securite que le Modbus depuis la page web. Le lot « donnees » garde donc le local pur (JSON, expressions regulieres), qui couvre l'essentiel : lire un fichier JSON/CSV lie, analyser une trame texte.

Les neuf concepts

L'ordre de codage (pour que les lots ne se marchent pas dessus)

  • 1erreurs — L'objet-erreur (Code, Message) d'abord : LEVER, WAIT_UNTIL, JSON, les tests s'y accrochent.
  • 2generiques — Le champ manquant sur les fonctions, avant que les objets et les unites ne touchent le verificateur.
  • 3objets — Les methodes, l'heritage, les interfaces - le plus gros du moteur et des ecrans.
  • 4unites — Les unites s'appuient sur le verificateur deja etendu.
  • 5bibliotheques — Les espaces de noms et les bibliotheques reliees - le plus profond, en dernier.
  • //debogueur · tests · donnees — En parallele apres l'etape 1 : ils ne touchent pas le format du projet.

⚠  Lever ses erreurs + attendre une condition (LEVER / RELEVER / WAIT_UNTIL) gros

Tu lèves tes propres erreurs avec un code et un message que le CATCH relit, et tu attends qu'une condition devienne vraie sans figer l'IHM.

FUNCTION Verifier_Niveau(n : REAL)
    IF n < 0.0 OR n > 100.0 THEN
        LEVER('E_Niveau', 'niveau hors plage : {n:0.0} %');
    END_IF;
END_FUNCTION

TRY
    Verifier_Niveau(Niveau_Cuve);
CATCH e
    IHM_LOG(WARNING, '{e.Code} (ligne {e.Ligne}) : {e.Message}');
    IF e.Code = 'E_Niveau' THEN
        Alarme_Niveau := TRUE;
    END_IF;
END_TRY
Generer — rien a signaler

Le message interpole {expr[:format]} comme IHM_JOURNAL/IHM_LOG : il est figé au moment du LEVER (ici {n} vaut la valeur passée). e est un T_Erreur en lecture seule : e.Code, e.Message, e.Ligne ; e tout court = e.Message.

TRY
    Charger_Recette(Nom_Recette);
CATCH e
    IHM_JOURNAL('Échec du chargement : {e.Message}');
    RELEVER;   (* même code, même message, même ligne : au TRY du dessus *)
END_TRY
Generer — rien a signaler

RELEVER sans argument réémet l'erreur courante vers le TRY englobant, ou arrête le script si aucun. Hors d'un CATCH, Compiler le refuse.

TRY
    Consigne := DYNAMIC_CAST<INT>(Valeur_Lue);   (* 40000 : refusé *)
    Debit := Mesures['debit'];                   (* clé absente *)
CATCH e
    (* e.Code = 'E_CONVERSION' puis 'E_CLE' selon la faute *)
    IHM_LOG(WARNING, e.Message);
END_TRY
Generer — des refus a leur ligne (vois les commentaires REFUSÉ dans le code)

Les erreurs du moteur (division par zéro E_DIVISION, hors bornes E_BORNE, DYNAMIC_CAST E_CONVERSION, clé absente E_CLE, ASSERT E_ASSERT, autre E_MOTEUR) portent un code stable ; e.Message reste le message français de la 1.12.1.

(* Script Sequence_Remplissage : Détaché, déclencheur Appelé *)
Vanne_Entree := TRUE;
WAIT_UNTIL(Niveau_Cuve >= Consigne_Niveau, T#2m);   (* 2 min au plus *)
Vanne_Entree := FALSE;
IHM_JOURNAL('Remplissage terminé : {Niveau_Cuve:0.0} %');
Generer — rien a signaler

La condition est revérifiée à chaque reprise de la tâche (l'IHM respire entre deux essais) ; en instruction, un délai dépassé lève E_ATTENTE (que TRY rattrape).

IF WAIT_UNTIL(Pression_Etablie, T#10s) THEN
    Pompe := TRUE;
ELSE
    IHM_LOG(ERROR, 'Pression non établie après 10 s : arrêt de la séquence');
END_IF;
Generer — rien a signaler

Dès que sa valeur est employée (IF, affectation, argument), WAIT_UNTIL rend TRUE si la condition est devenue vraie, FALSE au délai : pas d'erreur. Sans délai, WAIT_UNTIL(cond) attend indéfiniment (IHM_SCRIPT_ARRETER l'arrête).

TRY
    Ouvrir_Vanne_Gaz();
    WAIT_UNTIL(Capteur_Vanne_Ouverte, T#5s);   (* instruction : E_ATTENTE au bout de 5 s *)
CATCH e
    Defaut_Vanne := TRUE;
    LEVER('E_Securite', 'vanne gaz non confirmée ouverte ({e.Code}) : mise en sécurité');
END_TRY
Generer — rien a signaler

Un CATCH peut relever une erreur d'un autre code : ici E_ATTENTE devient E_Securite pour l'appelant.

Ce qui se passe

  • LEVER('Code', 'Message') et LEVER('Code') sont des INSTRUCTIONS du dialecte IHM (comme RETURN, TRY, CONTINUE), réservées au ST de l'IHM (jamais au ST de l'automate). Le code est un texte non vide (convention : préfixe E_ en MAJUSCULES, ex. E_Niveau) ; le message est optionnel et interpole {expr[:format]} comme IHM_JOURNAL. L'interpolation est faite au moment du LEVER, le texte final est figé.
  • Dans un TRY, LEVER se comporte comme une erreur du moteur : le corps s'arrête, le CATCH s'exécute. Hors de tout TRY, le script s'arrête à cette ligne et la Console affiche « E_Niveau : niveau hors plage : 3 % (ligne 12) » comme pour les autres erreurs ; un script détaché se termine sur cette erreur.
  • La variable du CATCH (CATCH e) est un objet T_Erreur en LECTURE SEULE, créé le temps du handler : e.Code (STRING), e.Message (STRING), e.Ligne (DINT) ; e seul se lit comme e.Message (compatible avec le CATCH Erreur de la 1.12.1 qui recevait déjà le message). Écrire e, e.Code… est refusé (« e est l'erreur attrapée, en lecture seule »). Un autre membre : « T_Erreur n'a que Code, Message et Ligne ».
  • Compatibilité 1.12.1 : si le nom après CATCH est une variable locale STRING déjà déclarée, il reçoit le message comme avant (aucun .Code) ; si le nom n'est pas déclaré (le cas recommandé, CATCH e), c'est l'objet T_Erreur. CATCH sans nom reste permis (on n'inspecte pas l'erreur).
  • RELEVER (sans argument) réémet l'erreur courante — même code, même message, même ligne — vers le TRY englobant, ou arrête le script s'il n'y en a pas. RELEVER n'est permis que dans le bloc d'un CATCH : ailleurs, Compiler dit « RELEVER n'est permis que dans un CATCH ». Pour changer de code, on fait un nouveau LEVER.
  • TRY imbriqués : un LEVER (ou une erreur) du CATCH intérieur remonte au TRY extérieur ; la profondeur et l'erreur gardée sont empilées comme en 1.12.1, avec le code en plus.
  • WAIT_UNTIL(condition [, délai]) est une native (groupe « attente », comme WAIT) qui rend un BOOL. La condition doit être un BOOL ; elle est RÉÉVALUÉE à chaque reprise de la tâche (le délai, s'il est donné, est un TIME ou un nombre de millisecondes ≥ 0). TRUE : la condition est devenue vraie ; FALSE : le délai est dépassé.
  • WAIT_UNTIL est sensible au contexte, comme une procédure/fonction : si sa valeur est EMPLOYÉE (IF, affectation, argument), un délai dépassé rend FALSE sans erreur ; si elle est IGNORÉE (instruction seule) avec un délai, un délai dépassé LÈVE E_ATTENTE (« la condition n'est pas devenue vraie en 5 s »), rattrapable par TRY. Sans délai, WAIT_UNTIL(cond) attend indéfiniment (seul IHM_SCRIPT_ARRETER ou l'arrêt de l'IHM y met fin).
  • Détaché obligatoire en pratique : dans un script détaché, WAIT_UNTIL rend la main entre deux essais, l'IHM continue (vues, communication, autres scripts), donc la condition peut évoluer. Dans un script non détaché, l'IHM est figée pendant l'attente : la condition ne bougera pas — Compiler avertit « WAIT_UNTIL dans un script non détaché : l'IHM est figée, la condition ne changera pas ; coche Détaché » et l'attente est plafonnée à 10 s comme WAIT.
  • Dans une expression (fx), WAIT_UNTIL, LEVER et RELEVER sont refusés, exactement comme WAIT (« une expression ne lève pas d'erreur / n'attend pas »).
  • La condition d'un WAIT_UNTIL doit être une pure lecture : si elle contient un appel qui écrit (effet de bord), il est rejoué à chaque essai — un avertissement le signale si c'est détectable.
  • Aucune montée du format projet : LEVER/RELEVER/WAIT_UNTIL ne sont que du texte dans le corps du script, l'objet T_Erreur est purement d'exécution. Un projet d'avant se relit sans migration.

Ou ca se voit, dans l'editeur

  • Éditeur de scripts (Programmation générale › Scripts, scripts de vue, fonctions, opérateurs) — LEVER et RELEVER colorés en mot-clé comme TRY/CATCH ; WAIT_UNTIL coloré en native comme WAIT. Soulignement ondulé en direct : RELEVER hors d'un CATCH, condition non BOOL, WAIT_UNTIL dans une expression, mauvais type d'argument — avec ligne, colonne et message aux Diagnostics du panneau du bas.
  • Aide à la saisie (complétion dans l'éditeur) — Taper LE propose le modèle LEVER('E_…', '…') ; RE propose RELEVER ; WAIT_U propose WAIT_UNTIL(condition, T#…). Après CATCH e, taper e. propose .Code, .Message, .Ligne. Le modèle inséré par TRY passe de « CATCH Erreur » à « CATCH e ».
  • Natives (Programmation générale › Natives) et « Choisir une fonction… » — Nouvelles fiches LEVER, RELEVER, WAIT_UNTIL dans le thème « attente / instructions », présentes dans « De A à Z » et dans le sélecteur modal (WAIT_UNTIL filtrable par « Rend : BOOL »). Une fiche de type T_Erreur (Code, Message, Ligne) dans l'onglet Types.
  • Propriétés d'un script général — Sous la case Détaché, un rappel « WAIT_UNTIL et les séquences ont besoin de Détaché » ; au besoin, un bouton « Cocher Détaché » proposé par le diagnostic quand un script non détaché emploie WAIT_UNTIL.
  • Panneau du bas › Console / Diagnostics (simulation) — Une erreur LEVÉE non rattrapée s'affiche « E_Niveau : niveau hors plage : 3 % » à sa ligne, comme les autres erreurs de script ; un WAIT_UNTIL en instruction dépassé affiche « E_ATTENTE : … (ligne N) ». L'outil « Pourquoi ? » montre le code et le message de la dernière erreur.
  • Simulation (arbre Simulation, Expressions) — Un script détaché arrêté dans un WAIT_UNTIL compte comme actif : IHM_SCRIPT_ACTIF rend TRUE, il apparaît dans la liste des scripts en marche ; dans Expressions, e.Code/e.Message sont lisibles au point où le handler s'exécute (avec le débogueur, lot J2).
  • Générer / Compiler (F7) et colonne État des scripts — Tous les scripts sont relus pour les nouvelles constructions ; les fautes (RELEVER hors CATCH, WAIT_UNTIL en fx…) remontent avec script, ligne et colonne ; la colonne État compte ces erreurs.

⟨⟩  Les fonctions génériques (TEMPLATE) partout gros

Écris une fonction une seule fois (Max, Limiter, Moyenne) et emploie-la sur n'importe quel type : T se déduit de tes arguments, et le sous-onglet Fonctions la gère comme les structures et symboles génériques d'aujourd'hui.

TEMPLATE <T : ANY_NUM> FUNCTION Max(a : T; b : T) : T
    IF a > b THEN Max := a; ELSE Max := b; END_IF
END_FUNCTION

(* appels *)
Pire   := Max(P_Armoire_A, P_Armoire_B);   (* T déduit : REAL *)
Rang   := Max<INT>(Rang_Lu, 0);             (* T donné : INT *)
Melange := Max(1, 2.5);                     (* OK : T = REAL (le réel l'emporte) *)
Generer — rien a signaler

Elle donne sa valeur par Nom := ... ou par RETURN, comme une fonction IHM ordinaire. Un paramètre répété (a, b) force le même T pour les deux arguments.

TEMPLATE <T> FUNCTION Valeur_De(m : T_Mesure<T>) : T
    Valeur_De := m.Valeur;
END_FUNCTION

TEMPLATE <T : ANY_NUM> FUNCTION Moyenne(mesures : LIST OF T) : REAL
    VAR total : REAL := 0.0; END_VAR
    FOR EACH x IN mesures DO total := total + TO_REAL(x); END_FOR
    Moyenne := total / SIZE(mesures);
END_FUNCTION
Generer — rien a signaler

T se déduit à travers T_Mesure<REAL> (unifyGeneric existe déjà), LIST OF T, ARRAY[..] OF T, et MAP[K] OF T (K = 2e générique).

TEMPLATE <T : ANY_MAGNITUDE> FUNCTION Limiter(x : T; bas : T; haut : T) : T
    IF x < bas THEN RETURN STATIC_CAST<T>(bas); END_IF
    IF x > haut THEN RETURN haut; END_IF
    RETURN x;
END_FUNCTION

Niveau_Bar := Limiter(Niveau_Brut, 0.0, 10.0);   (* T = REAL *)
Duree      := Limiter(T_Cycle, t#0s, t#30s);     (* T = TIME, ANY_MAGNITUDE l'accepte *)
Generer — rien a signaler

Contraintes disponibles : ANY, ANY_NUM, ANY_INT, ANY_REAL, ANY_BIT, ANY_STRING, ANY_DATE, ANY_DURATION, ANY_MAGNITUDE, ANY_ELEMENTARY, ANY_STRUCT, ANY_DERIVED.

Txt := Max('A', 'B');     (* refusé : Max : T = STRING n'est pas un ANY_NUM *)
r   := Zero<>();          (* refusé : Zero : le type T ne se déduit pas des arguments — donne-le : Zero<REAL>() *)
v   := Max(1);            (* refusé : Max attend 2 arguments *)
q   := Max<INT, REAL>(a); (* refusé : Max : 2 types donnés pour 1 (TEMPLATE <T...>) *)
Generer — des refus a leur ligne (vois les commentaires REFUSÉ dans le code)

Mêmes messages que le moteur produit déjà en simulation (sim/Interpreter.cpp), repris tels quels par le vérificateur de l'éditeur.

(* Fonctions de la vue Synoptique, Génériques : U : ANY_NUM *)
TEMPLATE <U : ANY_NUM> FUNCTION Formater(v : U; unite : STRING) : STRING
    Formater := TO_STRING(ROUND(TO_REAL(v), 2)) + ' ' + unite;
END_FUNCTION

(* ailleurs *)
Libelle := Synoptique.Formater(Debit_Four, 'm3/h');   (* U = REAL *)

Projet (Programmation générale › Fonctions), de vue, de popup, de symbole. Une fonction de symbole peut être virtuelle ET générique ; une redéfinition d'instance garde la même forme <U>.

TEMPLATE <T> FUNCTION Premier_Qui(liste : LIST OF T; test : CALLBACK (x : T) : BOOL) : T
    FOR EACH x IN liste DO
        IF test(x) THEN RETURN x; END_IF
    END_FOR
    RETURN liste[0];
END_FUNCTION

Armoire_HS := Premier_Qui(Armoires, LAMBDA (a : T_Armoire) : BOOL => a.Defaut);

Se marie aux rappels (1.12.19) : le CALLBACK porte T, et la LAMBDA passée fixe T = T_Armoire par déduction.

Ce qui se passe

  • Portée : une fonction IHM de projet, de vue, de popup ou de symbole peut porter ses propres génériques (TEMPLATE <T : contrainte, U, K>). Vide = fonction ordinaire, exactement comme avant (compatibilité totale).
  • Le moteur de simulation sait déjà tout faire (depuis 1.12.19, sim/Interpreter.cpp) : parse de TEMPLATE <...> FUNCTION, déduction par unify/unifyGeneric/bindTemplate, contrôle de contrainte (genericAccepts), types donnés F<INT>(...). Lot H1 n'ajoute AUCUN comportement de moteur ; il relie l'éditeur à ce moteur. Ce qui marche aujourd'hui : une fonction interne TEMPLATE écrite à la main dans le corps d'un script général tourne en simulation. Ce qui manque : la déclarer dans l'éditeur dédié (sous-onglet Fonctions, modale Nouvelle fonction) et que la vérification, l'aide à la saisie et Générer la suivent.
  • Déduction de T : à partir des types des arguments. 2 et 2.5 → REAL l'emporte (règle existante). Un même nom de générique sur plusieurs paramètres doit s'accorder (sinon le moteur prend REAL si entier+réel, refuse si incompatible). Un T qui n'apparaît dans aucun paramètre doit être donné entre chevrons, sinon refus avec l'exemple « donne-le : Nom<REAL>() ».
  • Contrainte : un seul générique des natives par paramètre (ANY_*). Un type hors contrainte est refusé avec « T = <type> n'est pas un <contrainte> ». Pas de contrainte multiple, pas de WHERE, pas de spécialisation : on reste au niveau des structures/symboles génériques existants.
  • Type de retour : peut être T (ou LIST OF T, un rappel sur T...). Dans une expression fx, le type du résultat est le T DÉDUIT à l'appel, pas la lettre T — sinon l'fx serait de type inconnu. STATIC_CAST<T>/DYNAMIC_CAST<T> dans le corps rendent le type déduit (déjà géré par le moteur).
  • Procédure générique (sans retour) permise : TEMPLATE <T> FUNCTION Tracer(v : T) — utile avec IHM_LOG.
  • Surcharge : deux fonctions de même nom dont l'une est générique se départagent par leur forme ; deux surcharges génériques de même forme sont refusées (règle hmi::overload inchangée). Une fonction de symbole virtuelle peut être générique, mais pas virtuelle+surchargée (règle existante conservée).
  • Interaction avec le composé/les références : T se déduit à travers T_Mesure<REAL> (structure générique), LIST OF T, ARRAY[0..9] OF T, MAP[K] OF T (K second générique), REF_TO T, et un paramètre rappel CALLBACK (x : T) : BOOL (le rappel/la LAMBDA passés fixent T).
  • Changer les génériques d'une fonction fait suivre ses emplois, comme pour les structures et symboles (HmiGenericEdit) : renommer T suit ses paramètres/son retour ; retirer/ajouter/déplacer un générique réécrit les arguments donnés des appels F<REAL>(...). Ctrl+Z reprend tout.
  • Refus côté éditeur alignés sur le moteur : nom de générique illisible, deux fois le même, contrainte inconnue (réutilise hmi::parseGenerics et ses messages). Un paramètre/retour/locale de type T est accepté dès que T est un générique déclaré de la fonction (aujourd'hui « type de retour non pris en charge : T »).

Ou ca se voit, dans l'editeur

  • Modale « Nouvelle fonction » (comme le créateur de variable, tâche #190) — Un champ « Génériques » (T, T : ANY_NUM, K, V) au-dessus du Retour, avec la même aide que l'inspecteur d'un type. Une fois rempli, la case Retour et les cases Type des paramètres ouvrent le sélecteur de types avec T et K en tête (puce Génériques).
  • Sous-onglet Fonctions (Programmation générale, et Fonctions d'une vue / popup / symbole) › inspecteur — Une propriété « Génériques » (texte éditable, parseGenerics/genericsText) dans la catégorie Fonction, exactement comme la propriété Génériques d'un type (HmiVariablePanes) et d'un symbole (HmiParamPanes). La grille Paramètres accepte T/K dans la colonne Type via le sélecteur de types.
  • Arbre des fonctions (liste violette des fonctions) — La fonction générique s'affiche Max<T> (chevrons), comme la liste des types montre T_Mesure<T>.
  • Aide à la saisie (fx, scripts, actions) et « Choisir une fonction… » — La fonction est proposée avec sa forme Max(a : T; b : T) : T ; à l'appel, une ligne d'indice « T · déduit de a » (comme l'inspecteur d'instance d'un symbole générique). Le filtre « Rend » classe un retour générique sous « selon T ».
  • Générer (en-tête C / C++ du projet) — Une fonction générique s'écrit template <typename T> T Max(T a, T b); en C++, et en C un commentaire + macro/_Generic (comme les structures génériques le font déjà). Un retour/paramètre sans équivalent C garde le commentaire existant.
  • Soulignement / panneau du bas (Compiler) — À l'appel : soulignement rouge et message si T hors contrainte, non déductible, mauvais nombre de types donnés — repris du moteur.

◉  Les objets : méthodes, membres privés, héritage, interfaces tres gros

Tes types IHM deviennent de vrais objets : tu leur donnes des méthodes qui voient leurs membres par SELF, tu caches ce qui est interne, tu fais hériter un type d'un autre et tu traites une liste hétérogène de pompes et de vannes par un contrat commun.

TYPE T_Pompe
    Nom     : STRING;
    Debit   : REAL;            (* m3/h *)
    Marche  : BOOL;
    PRIVATE Heures : REAL := 0.0;   (* vu des seules méthodes de T_Pompe *)

    METHOD PUBLIC Demarrer                 (* une procédure : Pompe1.Demarrer() *)
    METHOD PUBLIC VIRTUAL EnDefaut : BOOL  (* redéfinissable par un sous-type *)
    METHOD PRIVATE Journal
END_TYPE
Generer — rien a signaler

Comme pour une énumération, le TYPE … END_TYPE est l'APERÇU (ST | C | C++). Tu édites les membres dans la grille (nouvelle colonne Visibilité) et chaque corps de méthode dans son éditeur, exactement comme un opérateur.

(* Demarrer()  —  SELF : l'instance de T_Pompe (THIS vaut SELF) *)
IF SELF.Heures > 8000.0 THEN
    IHM_JOURNAL('{Nom} : révision due');   (* Nom = SELF.Nom *)
END_IF;
Marche := TRUE;                            (* écrit SELF.Marche *)

(* EnDefaut : BOOL  —  rend sa valeur par son nom, comme une fonction *)
EnDefaut := Marche AND Debit < 1.0;
Generer — rien a signaler

Un membre se lit par son nom (Debit) ou par SELF.Debit, qui lève toute ambiguïté avec une locale. SELF est passé en VAR_IN_OUT : une méthode qui écrit un membre le modifie vraiment. Une méthode procédure n'a pas de retour ; une méthode fonction rend par son nom (EnDefaut := …) ou RETURN.

Pompe1.Demarrer();                       (* une variable IHM de type T_Pompe *)
IF Pompes[3].EnDefaut() THEN
    Alarme_Pompe := TRUE;
END_IF;
Total := Total + Fours[f].Vanne_Entree.Debit_Reel();   (* sur un membre composé *)
Generer — rien a signaler

Mêmes règles d'appel que les fonctions IHM (arguments dans l'ordre ou nommés a := …). Depuis un script, une expression fx, une action, une autre méthode. Une méthode privée ne s'appelle que depuis une méthode du même type ; ailleurs : « Journal est privé dans T_Pompe ».

TYPE T_PompeDoublee EXTENDS T_Pompe      (* tous les membres et méthodes de T_Pompe *)
    Secours : BOOL;
    METHOD PUBLIC OVERRIDE EnDefaut : BOOL   (* redéfinit la virtuelle du parent *)
END_TYPE

(* corps de EnDefaut redéfinie *)
EnDefaut := SUPER.EnDefaut() AND NOT Secours;   (* rappelle le corps de T_Pompe *)
Generer — rien a signaler

OVERRIDE n'est permis que si la méthode du parent est VIRTUAL et garde la même signature ; sinon Générer le refuse et le dit. Un T_PompeDoublee passe là où un T_Pompe est attendu (vers le parent) ; l'inverse demande DYNAMIC_CAST. SUPER existe déjà pour les fonctions de symbole.

TYPE I_Demarrable INTERFACE              (* pas de données : des signatures *)
    METHOD Demarrer
    METHOD EnDefaut : BOOL
END_TYPE

TYPE T_Vanne IMPLEMENTS I_Demarrable     (* Générer vérifie qu'elle a les deux *)
    Position : REAL;
    ...
END_TYPE
Generer — rien a signaler

Une interface n'a ni membre ni corps : un quatrième genre de type IHM (après Structure, Énumération, Rappel). « T_Vanne déclare I_Demarrable mais n'a pas EnDefaut() : BOOL » si un contrat manque. Un type peut implémenter plusieurs interfaces.

VAR  Equipements : LIST OF REF_TO I_Demarrable;  END_VAR
LIST_ADD(Equipements, REF(Pompe1));
LIST_ADD(Equipements, REF(Vanne_Entree));
FOR EACH e IN Equipements DO
    e^.Demarrer();                       (* la méthode du type réel : Pompe ou Vanne *)
    IF e^.EnDefaut() THEN Defauts := Defauts + 1; END_IF;
    p := DYNAMIC_CAST<T_Pompe>(e^);      (* NULL si ce n'en est pas une *)
    IF p <> NULL THEN Debit_Total := Debit_Total + p^.Debit; END_IF;
END_FOR;
Generer — rien a signaler

Une interface ne s'emploie que par REF_TO (une instance a des données, pas un contrat) : v : I_Demarrable est refusé, « emploie REF_TO I_Demarrable ». e^.Demarrer() part sur le type RÉEL de la cible (dispatch dynamique par la référence). DYNAMIC_CAST<T>(x) rend NULL en cas d'échec (déjà 1.12.20) et TRY/CATCH attrape un cast refusé.

Ce qui se passe

  • MÉTHODE = une HmiFunction portée par le type (nouveau HmiType::methods, comme View::functions pour un symbole). Elle voit : SELF (l'instance, de type le porteur ; THIS en est l'alias), les membres par leur nom (SELF.X pour lever l'ambiguïté), ses VAR_INPUT / VAR_IN_OUT, ses locales, et les autres méthodes/opérateurs du type. SELF est passé en VAR_IN_OUT : écrire un membre le modifie pour de bon (comme a dans un opérateur composé +=).
  • Compilation : une méthode devient une FUNCTION interne sous un nom stable — METHODE_T_Pompe_Demarrer(VAR_IN_OUT SELF : T_Pompe [; paramètres]) [: Retour] — que l'interpréteur résout et appelle (resolveMethod/boundMethod), exactement comme operatorFunctionText/resolveOperator aujourd'hui. Aucune nouvelle instruction dans le corps : du ST ordinaire.
  • APPEL : chemin.Méthode(args) partout où le type est atteignable — variable IHM, case de tableau, membre composé, paramètre de vue/symbole. L'aide à la saisie et Générer suivent le même marcheur de chemin typé que m['k'][2].Membre (un seul endroit, partagé avec les génériques et les unités).
  • MEMBRE PRIVÉ : TypeMember gagne une visibilité (défaut Public, donc un projet d'avant est inchangé). Privé = lu/écrit des seules méthodes du MÊME type (pas des sous-types, pas de l'extérieur, pas des scripts, pas du Tableau ni des plumes). Refus hors méthode : « Heures est privé dans T_Pompe : il ne se lit que depuis ses méthodes ». La privacité ne touche PAS la place Modbus : un membre privé d'une structure liée garde son adresse (l'équipement le lit/écrit ; seul le code ST est contraint).
  • MÉTHODE PRIVÉE : réutilise HmiFunction::visibility (déjà là pour les fonctions de vue). Appelable depuis une autre méthode du type seulement ; dehors, refus nommé. Une méthode privée ne peut pas être virtuelle (rien à redéfinir de l'extérieur).
  • HÉRITAGE : HmiType gagne base (le nom du type parent ; vide = aucun). EXTENDS n'existe qu'entre STRUCTURES (ni énumération, ni rappel, ni interface). Le sous-type a tous les membres du parent (en tête, dans l'ordre : la place Modbus du parent d'abord), puis les siens ; il hérite de ses méthodes et peut en ajouter. Assignation T_Pompe := T_PompeDoublee copie la tranche parente (permise, montée) ; l'inverse est refusée (« écris un DYNAMIC_CAST pour descendre »).
  • REDÉFINITION : une méthode VIRTUAL du parent se redéfinit dans le sous-type par une méthode OVERRIDE de MÊME signature (même paramètres, même retour) ; SUPER.Méthode() rappelle le corps du parent. Refus : OVERRIDE sans VIRTUAL au parent, signature différente, OVERRIDE d'une méthode inexistante — chacun avec son message et le « veux-tu dire ? ».
  • DISPATCH DYNAMIQUE : une méthode virtuelle appelée à travers une REF_TO (base ou interface) part sur le type RÉEL de la cible de la référence — ce type est le type déclaré de la variable visée (une REF_TO garde déjà le chemin de sa cible, lot 7). Sur une variable non-référence, type réel = type statique : aucun surcoût, aucun tag caché à stocker (compatible avec les structures mises à plat et la liaison Modbus).
  • INTERFACE : quatrième HmiTypeKind (Interface). Elle porte une liste de signatures de méthodes (HmiFunction à corps vide) ; ni membre, ni donnée, ni place Modbus, ni valeur initiale. IMPLEMENTS (nouveau HmiType::interfaces, plusieurs) ; Générer vérifie la conformité (chaque signature présente, même retour et mêmes paramètres) et nomme ce qui manque. Une interface ne s'emploie que par REF_TO I_xxx, y compris dans un conteneur (LIST OF REF_TO I_Demarrable) : c'est ce qui permet la liste hétérogène ; v : I_Demarrable (donnée directe) est refusé.
  • RÈGLE DE CONVERSION (HmiTypeRegistry) : un nouveau cas « montée » — un sous-type vers un parent, et un type vers une interface qu'il implémente — au coût d'un élargissement (accepté en Référence et en passage d'argument, dans ce sens seulement). La descente (parent vers sous-type, interface vers type) est refusée sauf DYNAMIC_CAST. REF_TO I_xxx accepte une REF(x) de tout type qui implémente I_xxx.
  • CYCLES ET BORNES : un type ne peut pas hériter de lui-même, même par un détour (T_A → T_B → T_A) : refusé avec le chemin, comme le cycle de membres actuel. Un type qui s'étend reste soumis au refus d'auto-contenance des membres. Une interface ne peut pas EXTENDS ; une structure ne peut pas IMPLEMENTS un type qui n'est pas une interface.
  • DÉFINITION DANS LE MOTEUR : les types sont globaux au projet (pas de vue porteuse, contrairement aux fonctions de symbole) — resolveMethod part de Project, comme les opérateurs de type. Une méthode tourne en simulation (ST) ; en C / C++ elle est éditée et vérifiée, pas exécutée (comme tout le reste). API Studio ne définit pas de type IHM : son ST d'automate est intouché.
  • INTERACTION AVEC L'EXISTANT : les opérateurs de type (a, b, Resultat) restent tels quels et coexistent avec les méthodes (SELF) ; un opérateur peut appeler une méthode (a.Demarrer()). Les rappels (CALLBACK) et les membres objets (LIST/MAP) marchent dans un corps de méthode. Un type générique T_Mesure<T> peut porter des méthodes qui voient T (substitution partagée). Renommer un type suit base, interfaces, méthodes, SUPER et tous les appels chemin.Méthode(). Dupliquer un type copie ses méthodes (identifiants neufs).

⚖  Les unités de mesure dans les types gros

Donne une unité physique (bar, mbar, °C, m³/h, %, s) à une variable ou à un membre de type : la compilation refuse bar + mbar, convertit d'office ce qui est compatible, et l'unité remonte toute seule jusqu'à l'affichage - sans rien changer pour qui n'en met pas.

TYPE T_Ligne :
    Pression      : REAL [bar];
    PressionBasse : REAL [mbar];
    Debit         : REAL [m3/h];
    Temperature   : REAL [degC];
    Niveau        : REAL [%];
    Vannes        : ARRAY[1..3] OF REAL [bar];   (* unité de l'élément *)
END_TYPE
Generer — rien a signaler

L'unité s'écrit entre crochets APRÈS un type numérique (REAL, INT...). Pas de crochets = pas d'unité (comme avant). Dans la grille des membres, la colonne Type reste « REAL » et une colonne Unité tient « bar » ; « REAL [bar] » est la forme combinée montrée par l'aide à la saisie, le survol et le sélecteur.

(* Pression : bar  ·  PressionBasse : mbar *)
Ecart := Pression - PressionBasse;              (* REFUSÉ : bar et mbar ne s'additionnent pas *)
Ecart := Pression - EN(PressionBasse, 'bar');   (* bon : Ecart est en bar *)

IF Pression > PressionBasse THEN ...            (* REFUSÉ : compare bar et mbar *)
IF Pression > 9.0 THEN ...                      (* bon : 9.0 pris en bar (le littéral adopte l'unité) *)
IF Pression > Temperature THEN ...              (* REFUSÉ : pression et température, deux familles *)
Generer — des refus a leur ligne (vois les commentaires REFUSÉ dans le code)

Message : « bar et mbar ne s'additionnent pas : convertis l'un des deux, par exemple EN(PressionBasse, 'bar'). » La correction d'un clic (Ctrl+.) insère le EN(...). Un littéral sans unité (9.0) prend celle de l'autre opérande.

Pression := PressionBasse;        (* mbar -> bar : converti d'office (× 0,001), une info *)
PressionBasse := Pression;        (* bar -> mbar : converti d'office (× 1000) *)
Pression := Temperature;          (* REFUSÉ : pression <- température (familles différentes) *)
Pression := 2.5;                  (* bon : 2.5 pris en bar *)
NombreNu := Pression;             (* bon : la cible sans unité reçoit le nombre tel quel (info) *)
Generer — des refus a leur ligne (vois les commentaires REFUSÉ dans le code)

L'affectation est plus souple que l'addition (c'est le cœur du lot) : même famille, unités différentes = conversion automatique ; familles différentes = refus. Idem pour passer un argument à un paramètre qui exige une unité et pour le retour d'une fonction. Option projet « Unités strictes » : l'affectation exige alors EN(...) au lieu de convertir.

FUNCTION AlarmeHaute : BOOL
VAR_INPUT p : REAL [bar]; END_VAR
    AlarmeHaute := p > 9.5;        (* 9.5 en bar *)
END_FUNCTION

Alerte := AlarmeHaute(PressionBasse);              (* mbar -> bar : converti d'office *)
Alerte := AlarmeHaute(EN(PressionBasse, 'bar'));   (* bon, explicite *)
Texte  := TO_STRING(EN(Temperature, 'K'));         (* °C -> K : affine (+ 273,15) *)
Generer — rien a signaler

EN(valeur, 'unité_cible') : la cible doit être de la même famille que l'unité de la valeur, sinon « on ne convertit pas des bar en °C ». La température est affine (facteur ET décalage). EN() d'une valeur sans unité : « EN demande une valeur qui porte une unité ».

Force    := Pression * 1.5;                         (* bar (× un nombre) : reste bar *)
Ratio    := Debit / DebitMax;                       (* m3/h / m3/h : SANS UNITÉ (rapport) *)
Taux     := EN(Debit, 'm3/h') / EN(DebitMax, 'm3/h') * 100.0;   (* un % *)
Produit  := Pression * Debit;                       (* bar × m3/h : unité perdue (info), un nombre nu *)
Brut     := SANS_UNITE(Pression);                   (* enlève l'unité volontairement : un REAL nu *)
Label    := UNITE(Pression);                        (* STRING : 'bar' *)
Generer — rien a signaler

* par un nombre garde l'unité ; / de deux mêmes unités donne un nombre sans unité ; un produit/division sans règle simple perd l'unité avec une info (pas d'algèbre d'unités composées type « bar·m »). SANS_UNITE et UNITE sont deux natives d'appoint.

IHM_JOURNAL('Pression ligne : {Pression:u}');   (* "9.08 bar" : l'unité vient du type *)
IHM_JOURNAL('Niveau : {Niveau:u}');             (* "60.0 %" *)
Generer — rien a signaler

L'unité physique du membre/de la variable devient l'unité d'affichage PAR DÉFAUT : {X:u}, l'afficheur, la jauge, le champ de saisie et la ligne « Unités et formats » la prennent sans qu'on la retape. Une ligne « Unités et formats » qui pose une autre unité l'emporte pour l'affichage seulement (et doit être de la même famille, sinon Générer le dit).

Ce qui se passe

  • Optionnel et rétro-compatible : une unité vide = exactement le comportement d'aujourd'hui. Rien n'est imposé à un projet existant ; aucun calcul ne change tant qu'aucune unité n'est posée.
  • Une unité ne se pose que sur un type NUMÉRIQUE (REAL, LREAL, INT et toute la famille entière/réel via typereg::isNumber). Sur un BOOL, un STRING, une structure, un tableau d'autre chose, un conteneur : refusé par Générer (« une unité ne va que sur un nombre »). Sur une case d'un ARRAY OF REAL : l'unité porte sur l'élément.
  • Bibliothèque d'unités (hmi::units) : des FAMILLES (dimensions) - pression, température, débit, temps, longueur, masse, tension, courant, fréquence, pourcentage... Chaque famille a une unité de référence ; chaque unité a une conversion affine vers la référence (facteur, décalage). bar/mbar/Pa/hPa/psi = facteur seul ; degC/K/degF = facteur ET décalage. Fournie d'office, enrichissable par le projet.
  • DEUX règles, volontairement différentes (le cœur du lot, mot pour mot avec la demande) : l'ADDITION/SOUSTRACTION/COMPARAISON (+, -, <, >, =, MIN, MAX, LIMIT) exige la même unité exacte - même famille mais unité différente = ERREUR, il faut EN(...). L'AFFECTATION (:=, passage d'argument, RETURN) de même famille CONVERTIT d'office (une info), ou exige EN(...) si l'option projet « Unités strictes » est cochée.
  • Familles différentes = toujours refusé, et la raison nomme les deux familles (« tu compares une pression et une température »). Une valeur sans unité se mêle à n'importe quelle unité : un littéral ou une variable nue adopte l'unité de l'autre opérande / de la cible ; une cible sans unité reçoit le nombre nu (info).
  • Multiplication/division : × ou / par un nombre sans unité garde l'unité ; a / b de la même unité donne un rapport SANS unité ; les autres produits/divisions perdent l'unité (un nombre nu) avec une info - pas d'unités composées (« bar·m », « m/s ») dans ce lot, on reste simple et prévisible.
  • Trois natives, au catalogue IHM (dialecte, jamais côté automate) : EN(x, 'unité') -> REAL converti (même famille obligatoire) ; UNITE(x) -> STRING (le symbole de l'unité de x, '' si aucune) ; SANS_UNITE(x) -> REAL nu. EN est la conversion explicite partout où une règle refuse.
  • L'unité est une propriété du CRÉNEAU (la déclaration), PAS de la valeur : sim::Value n'est pas touché. Tout le raisonnement est statique (exprcheck/scriptcheck) ; à l'exécution, le compilateur a pré-calculé l'affine (facteur, décalage) et l'accroche au nœud d'affectation/appel/retour qui convertit - le moteur applique une multiplication/addition triviale, inerte quand il n'y a pas d'unité.
  • Cas limite température : la conversion est affine, mais additionner deux températures absolues n'a pas de sens physique. L'addition reste permise (même unité) mais Générer prévient en information sur une addition de deux grandeurs à décalage (degC, degF) ; la soustraction de deux températures donne un écart (toujours permis). À documenter clairement dans l'aide.
  • Pourcentage et grandeurs « normalisées » : % est une famille sans dimension (EN(x,'ratio') = × 0,01). Nm³/h (débit normalisé) n'est PAS un simple facteur de m³/h : il est fourni comme une unité/famille à part, non convertible automatiquement (sinon on mentirait sur les conditions normales) ; Générer refuse EN(debit_Nm3h, 'm3/h') avec la raison.
  • Génériques (accord avec J7) : un membre d'une structure générique de type T peut porter une unité seulement si la contrainte de T est numérique (ANY_NUM, ANY_REAL, ANY_INT) ; sinon avertissement. L'unité est orthogonale à T : T_Mesure<T> avec un membre REAL [bar] marche ; une unité sur un paramètre de type T générique suit la même règle.
  • Objets et méthodes (accord avec J1) : le retour et les paramètres d'une méthode (Pompe.Debit() : REAL [m3/h]) portent une unité comme une fonction ; SELF.membre garde l'unité du membre. Les opérateurs d'un type IHM (a, b, Resultat) connaissent l'unité de leurs opérandes (a.Pression est en bar), donc un opérateur hérite des mêmes contrôles.
  • Rappels et références : un CALLBACK (x : REAL [bar]) : BOOL exige l'unité sur son argument à l'appel ; une REF_TO d'un membre uni porte l'unité du membre pointé (lecture/écriture convertissent comme une affectation).
  • Énumérations : jamais d'unité (ce sont des codes). Les enums natives et les types DATE/TIME ne prennent pas d'unité (TIME a déjà ses millisecondes ; la famille « temps » en unités s'applique aux REAL/INT qui comptent des secondes, pas au type TIME).
  • Affichage unifié : l'unité physique devient l'unité d'affichage par défaut (hmi::display::displayOf consulte d'abord le créneau, puis la ligne « Unités et formats »). {X} garde le format, {X:u} ajoute l'unité, un format écrit ({X:0.0}) garde le sien. Une ligne « Unités et formats » peut encore poser une unité d'affichage, mais elle doit être de la même famille que l'unité physique (sinon Générer : « tu affiches en mbar une variable en bar - c'est converti » en info, « en °C une variable en bar » en erreur).

Ou ca se voit, dans l'editeur

  • Variables IHM (grille + modal « Nouvelle variable ») — La même colonne/case Unité à côté du type, seulement active pour un type numérique (grisée sinon). La valeur initiale et les seuils se lisent dans cette unité.
  • Grilles de déclarations des éditeurs (constantes, variables, VAR locales, paramètres) — Colonne Unité dans la grille déballée (HmiDeclEdit) des scripts, fonctions, opérateurs, constantes de vue. Un paramètre VAR_INPUT p : REAL [bar] se tape ici.
  • Modal « Nouvelle fonction » (et le retour d'une fonction/méthode) — Un champ Unité à côté du type de retour (Rend : REAL [m3/h]) ; actif seulement si le retour est numérique.
  • Sélecteur d'unités (nouveau, modal léger façon sélecteur de type) — Recherche sans casse/accents, familles en catégories, Récents ; chaque unité montre son symbole, sa famille et sa référence ; « Nouvelle unité… » et « Nouvelle famille… » pour enrichir la bibliothèque du projet.
  • Configuration › Unités de mesure (nouvelle page, voisine d'Unités et formats) — La bibliothèque : familles, unité de référence, chaque unité avec facteur et décalage, fournie (verrouillée) ou du projet. Ajouter/Modifier/Retirer (une unité employée ne se retire pas, comme un type) ; Ctrl+Z.
  • Configuration › Unités et formats — La colonne Unité montre en gris l'unité physique héritée du créneau ; la taper en force une autre (même famille) pour l'affichage. Une case « Unités strictes » du projet (l'affectation exige EN au lieu de convertir).
  • Éditeur de scripts : aide à la saisie, survol, marge — Le type montré avec l'unité : « Pression : REAL [bar] ». EN( propose les unités de la même famille que l'argument. Soulignement des incohérences pendant la frappe, avec la correction d'un clic (insérer EN(...)).
  • Diagnostics / Compiler / Générer (panneau du bas) — Les incohérences d'unité à leur ligne/colonne, un double-clic y mène ; Ctrl+. applique EN(...). Les infos de conversion automatique (« mbar converti en bar ») listées en information.

Les lignes cas_test / arg / pose / verif suivent la fonction porteuse, comme les lignes declaration (1.11.18). La cle est l'id de la fonction : chaque surcharge garde ses propres cas. Un argument par ligne -> pas de collision avec les virgules d'un littera de structure.

Ce qui se passe

  • Un cas = nom + une liste d'arguments (un par parametre, dans l'ordre de l'onglet Parametres) + un resultat attendu + une tolerance (REAL) + des poses (valeurs mises avant l'appel) + des verifs (post-conditions) + actif/inactif + une description. Il s'attache a UNE fonction precise (par son id) : fonction du projet, de vue, de popup, de symbole ; les surcharges d'un meme nom ont chacune leurs cas.
  • Rejoue sur un banc, sans ecran : un Runtime neuf (comme runScenario), bind au projet et a l'automate simule s'il tourne (lecture seule, TrialPlc), prime() remet les variables IHM a leur valeur initiale, les POSES ecrivent leurs variables, puis runFunction(id, arguments) exactement comme l'Essai existant. Rien du projet ni de la simulation n'est touche.
  • Verdict par cas, meme vocabulaire que les essais de reception : reussi, echec, erreur, non joue (reutilise hmi::Verdict et verdictLabel). reussi = le retour tient dans la tolerance et toutes les verifs passent ; echec = une valeur fausse (le detail dit attendu vs obtenu) ; erreur = la fonction s'arrete (division par zero, hors bornes, argument illisible) alors qu'aucune erreur n'etait attendue, ou une erreur d'un autre code que l'attendu.
  • Comparaison du retour : REAL/LREAL avec |obtenu - attendu| <= tolerance (tolerance vide = egalite stricte) ; tout autre type (INT, BOOL, STRING, DATE, duree, enum, structure, tableau, LIST, MAP, TUPLE) en egalite exacte de sim::Value (son formatValue sert au detail). Une fonction sans retour (procedure) ne compare pas de retour : son attendu est fait de verifs.
  • Les POSES acceptent un chemin complet : une variable IHM, un membre, une case (Four1.Vannes[1].Position), une variable de l'automate lue (API.Pompe.Debit : lecture seule, on ne force que la copie du banc). Chaque pose se lit dans le type de sa cible (la regle des cases). Poser une variable inconnue, ou une valeur du mauvais type : Generer le refuse et le souligne dans la grille.
  • Les VERIFS, apres l'appel : une variable = une valeur attendue (avec sa tolerance pour un REAL), ou la cible speciale JOURNAL contient un texte (ce que la fonction a ecrit par IHM_JOURNAL / IHM_LOG). Plusieurs verifs par cas ; toutes doivent passer.
  • Rejoue AUTOMATIQUEMENT : a chaque Compiler (et Generer-et-compiler) et au Demarrer de la simulation, tous les cas actifs tournent, apres la verification du code. Par defaut un cas en echec est un AVERTISSEMENT (il ne bloque pas) ; une case de Configuration « Un test en echec empeche le demarrage » le rend bloquant. Une case « Rejouer les tests au demarrage » (cochee par defaut, decochable pour un gros projet ou la page web) evite de payer le cout a chaque lancement.
  • A la main : le bouton « Lancer les tests » du volet Fonctions (tous), « Lancer ce cas » dans le detail, double-clic sur une ligne de cas. Le resultat part aux Sorties du panneau du bas, categorie Tests (comme l'Essai part aux Sorties) ; la barre d'etat du volet compte « 7 cas . 6 reussis, 1 echec ».
  • Generer (checkFunctionTests) signale, sans jouer : un cas avec le mauvais nombre d'arguments (la signature a change), un argument/attendu/pose/verif illisible, une pose ou une verif sur une variable inconnue, une tolerance non numerique, un cas sans nom, deux cas du meme nom dans une fonction, un attendu sur une procedure (sans retour). Ces controles soulignent la case fautive dans la grille Tests.
  • Renommer la fonction ne touche pas ses cas (ils la designent par id). Renommer une VARIABLE met a jour les poses, verifs, arguments et attendus qui la citent (via HmiRenameRefs, comme les appels de fonction) ; un seul Ctrl+Z reprend tout. Dupliquer une fonction (Moyenne_copie) copie aussi ses cas (ids neufs). Supprimer un parametre previent si des cas lui donnaient un argument.
  • Export : « Rapport des tests » en CSV, Excel ou PDF, reutilisant ExportTable - une fonction (Cas, Arguments, Attendu, Verdict, Detail, Duree) ou toute la campagne (Fonction, Cas, Verdict, Detail), avec le bilan en sous-titre, comme reportTable des essais. Le dossier exports/.
  • Deux choses distinctes, clairement separees : les ESSAIS DE RECEPTION (IHM > Essais) rejouent l'operateur sur l'IHM en marche (ouvrir une vue, cliquer, signer) ; les TESTS UNITAIRES testent une FONCTION seule, sans vue, sans operateur. L'aide et le volet le disent pour ne pas les confondre.

Ou ca se voit, dans l'editeur

  • Editeur d'une fonction (Programmation generale > Fonctions, et le sous-onglet Fonctions d'une vue / popup / symbole) : un 5e onglet de code — Un onglet « Tests » a cote de Code | Parametres | Locales | Constantes (HmiCodeTabs). Il montre la grille des cas de la fonction : colonnes Cas (nom), Arguments (resume « 12.0 ; 20.0 ; 0.25 »), Attendu, Tol., et une pastille Verdict (vert reussi / rouge echec / orange erreur / gris non joue). Boutons Nouveau cas, Dupliquer, Supprimer (Suppr), Lancer, Lancer tout.
  • Sous la grille Tests : le detail du cas choisi — Trois petits blocs : « Poser avant » (cible = valeur, +/-), « Arguments » (une case par parametre, pre-remplie avec le nom et le type du parametre, l'aide a la saisie comme un champ ST), « Verifier apres » (cible = attendu + tolerance, avec JOURNAL dans la liste). En bas, la derniere execution : « attendu 18.0 — obtenu 18.0 (ecart 0.0) : reussi », ou le detail de l'echec/erreur a la ligne fautive. Un bouton « Lancer ce cas ».
  • L'arbre du projet (explorateur), sous une fonction depliee — Un noeud « Tests » sous la fonction (a cote de ses Parametres, Variables locales, Constantes deja deplies depuis 1.11.21) : « Tests · 7 cas · 6 reussis, 1 echec », chaque cas dessous avec sa pastille. Un clic ouvre l'onglet Tests sur ce cas. Une fonction avec un cas en echec porte une pastille rouge dans l'arbre.
  • Barre d'outils du volet Fonctions + barre d'etat — Un bouton « Lancer les tests » (joue tous les cas de toutes les fonctions du volet). La barre d'etat ajoute le compte global : « 24 cas . 22 reussis, 1 echec, 1 erreur » ; un clic mene aux Sorties filtrees sur les echecs.
  • Panneau du bas, categorie « Tests » (a cote de Sorties / Console / Diagnostics) — A chaque Compiler/Demarrer et a chaque lancement manuel : une ligne par cas (gravite + « Moyenne_Pression / poids 25 % : reussi (18.0) » ou « … : echec, attendu 18.0, obtenu 17.5 »). Un clic ouvre la fonction sur l'onglet Tests, le cas selectionne. Filtre « Echecs seulement ».
  • Configuration de l'IHM (sous le cycle) — Deux cases : « Rejouer les tests des fonctions au Compiler/Demarrer » (cochee) et « Un test en echec empeche le demarrage de la simulation » (decochee). Et dans la barre, un bouton « Rapport des tests… » (CSV / Excel / PDF).
  • Fenetre « Nouveau cas » (modale, comme Nouvelle fonction) — Le nom du cas, une description ; la grille des arguments pre-remplie d'apres la signature (nom, type, defaut) ; un apercu de l'appel « Moyenne_Pression(12.0, 20.0, 0.25) ». Pour une fonction generique (lot TEMPLATE), une case T := … si T ne se deduit pas des arguments.

Pose un point d'arrêt dans la marge d'un script IHM : en simulation, le moteur s'arrête vraiment dessus. Tu vois la pile des appels, tes variables locales et tes espions, et tu avances pas à pas - Entrer, Sortir, Suivant.

(* Script Statistiques_Pression - clic dans la marge, ligne « IF P < Mini » : un rond rouge *)
P := Armoires[0].ana.PT1.mes;
Tours := Tours + 1;
IF P < Mini THEN          (* <-- le moteur s'arrête AVANT cette instruction *)
    Mini := P;
END_IF;
Generer — rien a signaler

En pause ici, le volet Débogage montre les locales (P, Tours, Mini, Maxi), les espions, la pile, et la valeur de chaque nom de la ligne à droite du code. Rien n'est écrit tant qu'on ne continue pas.

(* Condition tapée au clic droit sur le point : il ne s'arrête que si elle est vraie *)
P < 5.0 OR Tours MOD 100 = 0

Lue une fois quand on la pose, essayée à chaque passage ; un nom inconnu se dit tout de suite - « Presion n'est pas déclarée ici ; il ne s'arrêtera pas » - et le rond passe en gris (réutilise la francisation de RuntimeDebug).

FOR f := 1 TO Fours.High DO
    IHM_POINT_ARRET(Fours[f].Temperature > 900.0);   (* s'arrête au 1er four trop chaud *)

IHM_POINT_ARRET sans argument s'arrête à coup sûr ; avec un BOOL, seulement s'il est vrai. Pratique dans une boucle ou un script détaché. Hors simulation (poste, page web) il ne fait rien.

(* « Entrer » (F11) sur cette ligne descend dans le corps de Moyenne_Pression *)

(* Script détaché, déclencheur Appelé *)
Vanne_Entree := TRUE;

« Suivant » enjambe le WAIT : l'IHM respire pendant l'attente (elle n'est pas figée), puis le moteur se réarrête à la ligne d'après. On réutilise le fil de ScriptTask (1.12.26).

Ce qui se passe

  • Portée : SIMULATION de l'IHM seulement, et scripts ST seulement (généraux, de vue OnOpen/OnCycle/OnClose, fonctions IHM, de vue, de symbole, fonctions internes, opérateurs). Un script C/C++ n'est pas exécuté : sa marge refuse le point et dit « non exécuté en simulation (C/C++) ».
  • Poser un point d'arrêt : clic dans la marge gauche de l'éditeur de script/fonction (un rond rouge, à côté des numéros de ligne et des marques de diagnostic) ; re-clic l'enlève. Aussi : Simulation › Débogage › « + Point d'arrêt » tapé (« Statistiques_Pression 14 », « ... 14 si P < 5 »). Une ligne sans instruction décale le point à l'instruction suivante (statementLines), avec une note « décalé à la ligne 15 ».
  • La PAUSE est réelle, au milieu de l'exécution - à la différence du débogueur de l'automate qui ne s'arrête qu'en fin de cycle. Le script débogué tourne sur un fil ScriptTask : au point d'arrêt, Env::breakpointReached fait yield(), le fil de l'IHM reprend la main, affiche l'état et continue de peindre (dernière image figée) tout en répondant à la barre de débogage. Un seul fil tourne à la fois : la mémoire reste cohérente, rien à verrouiller.
  • Coût nul quand on ne débogue pas : sans point armé ni pas demandé, les scripts tournent comme aujourd'hui (runScriptHere, sur le fil de l'IHM). Le fil ScriptTask et setBreakLines ne s'activent qu'avec au moins un point armé sur le script, ou un pas en cours - exactement l'esprit de « le coût d'une section sans point d'arrêt est nul ».
  • Pas à pas : Suivant (F10, par-dessus : l'instruction suivante de la même frame, un appel s'exécute entier), Entrer (F11, descend dans la fonction IHM / interne / l'opérateur appelé sur la ligne), Sortir (Maj+F11, jusqu'au retour dans l'appelant), Continuer (F5). Entrer sur une native ou une fonction sans corps ST se comporte comme Suivant. Le pas se règle par une directive (profondeur de frame visée) relue dans breakpointReached, qui re-yield au bon moment.
  • Pile d'appels : construite depuis le contexte que le moteur tient déjà (ExecState.frames + trace_) : cycle IHM / action (Clic de Vue_A/Btn_Marche) / script détaché en bas, puis script › fonction IHM › fonction interne › opérateur › LAMBDA. Chaque niveau est cliquable : on voit son code (lecture seule, ligne surlignée) et ses locales. Les noms suivent l'espace de noms (J8 : Util.Moyenne) et les méthodes/SELF (J1).
  • Valeurs au point d'arrêt : (1) LOCALES de la frame choisie - VAR, VAR_TEMP, VAR_INPUT, compteur de FOR, clé/valeur de FOR EACH - lues en direct dans les Locals (RunLimits.locals) ; un scalaire inline, une structure/MAP/LIST/tableau se déplie comme l'arbre Automate. (2) VALEURS DE LA LIGNE à droite du code (LineProbe.lineValues, indices évalués : Armoires[2].etat). (3) ESPIONS et chemins du projet (variables IHM, automate) lus en direct. Une valeur forcée est marquée « (forcée) ».
  • En pause, on peut agir : Forcer une valeur ou modifier une variable surveillée (comme le débogueur de l'automate) ; « Modifier le projet » ouvre le script à sa ligne. Mais reprendre après une modif du CORPS du script débogué ne peut pas reprendre en milieu de ligne (le programme a changé) : message « le script a changé : il reprendra au prochain cycle » - plus prudent que la reprise au même cycle de l'automate (qui ne fait que reprendre les valeurs).
  • Le chien de garde et les budgets sont suspendus pendant la pause (comme un WAIT : holdWatchdog) : une longue pause ne déclenche pas la fenêtre de blocage. Une condition qui lève une erreur à l'évaluation (indice hors bornes pour cette instance) désarme le point et le dit - « condition invalide : indice hors bornes ; il ne s'arrêtera pas ».
  • Refusé, avec message : un point/un IHM_POINT_ARRET atteint dans une fonction appelée par une EXPRESSION (fx, readOnly_ > 0) ne s'arrête pas (il ne peut pas rendre la main sans danger, comme WAIT) - la barre dit « appelée par une expression : pas d'arrêt ». IHM_POINT_ARRET dans une expression est refusé par le checker, comme WAIT.
  • Un point d'arrêt suit le SCRIPT, pas son texte : il est repéré par l'id du script (et le numéro de ligne) ; renommer le script ou taper au-dessus du point le garde à sa place. S'il tombe sur une ligne sans instruction après une modif, il se re-décale et le signale.
  • Où vivent les points : dans la session de simulation (SimulationHost), pas dans le fichier projet - fermer le sous-onglet ne les enlève pas, Arrêter non plus. Ils sont retenus d'une séance à l'autre dans les réglages (par projet). IHM_POINT_ARRET, lui, EST dans le code enregistré (c'est une native).

Ou ca se voit, dans l'editeur

  • Marge de l'éditeur de scripts (IHM › Programmation générale › Scripts, et Vue › Scripts) — Une colonne de points d'arrêt à gauche des numéros de ligne (ui::MultiLineText) : clic pose/enlève un rond rouge ; la ligne en pause est surlignée en marche. Clic droit : Point d'arrêt (F9), Condition…, Désactiver, Exécuter jusqu'à la ligne, Retirer tous les points.
  • Marge des éditeurs de fonctions (fonctions IHM, de vue/popup, de symbole, opérateurs) — Même colonne et même menu : on pose un point dans le corps d'une fonction, qui s'arrête à chaque appel (toutes instances) ou pour l'instance affichée.
  • Sous-onglet Simulation › Débogage — Un sélecteur Automate | IHM en tête (comme les deux moitiés de la simulation). Côté IHM : la barre (Continuer F5, Suivant F10, Entrer F11, Sortir Maj+F11, Pause, Arrêter Maj+F5), l'état en clair (« En pause au point 2 : script Statistiques_Pression, ligne 14, cycle IHM 1 243 - P = 3,2 »), la liste des points (rond actif, script:ligne, condition modifiable, passages, croix), les espions dépliables, la pile cliquable, le code en lecture seule (ligne surlignée, valeurs à droite) et les Locales de la frame choisie.
  • Dialogue de la condition (SimConditionDialog réutilisé) — Le code de la ligne, le champ Condition avec aide à la saisie (noms du script + projet), les idées, et l'aperçu en direct « Maintenant, c'est vrai (P = 3,2) » / « Sans condition : il s'arrêtera à chaque passage ».

{ }  Données dans les scripts : JSON et expressions régulières gros

Tu lis et écris du JSON, et tu fouilles un texte au motif, directement dans tes scripts IHM — tout en local, sans réseau.

VAR
    Texte    : STRING;
    Recettes : LIST OF ANY;     (* un tableau JSON *)
    i        : DINT;
END_VAR
Texte := FILE_READ('recettes_gaz.json');   (* relatif à donnees/ du projet *)
Recettes := JSON_LIRE(Texte);              (* une LIST OF ANY *)
FOR i := 0 TO Recettes.Count - 1 DO
    IF JSON_BOOL(Recettes[i]['actif'], FALSE) THEN
        Consigne_Pression := JSON_NOMBRE(Recettes[i]['pression']);  (* ANY -> REAL *)
        Nom_Gaz           := JSON_TEXTE(Recettes[i]['gaz']);
    END_IF;
END_FOR;
Generer — rien a signaler

JSON_LIRE rend une valeur ANY : un tableau devient LIST OF ANY, un objet MAP[STRING] OF ANY. L'accès se fait par [index] et ['clé'], comme une liste et une MAP.

VAR Etat : MAP[STRING] OF ANY; END_VAR
Etat['armoire']  := 'A';
Etat['pression'] := Mesure_Pression;         (* un REAL dans une case ANY *)
Etat['alarmes']  := [Al_Haute, Al_Basse];    (* une liste -> tableau JSON *)
FILE_WRITE('etat_armoire.json', JSON_ECRIRE(Etat, TRUE));   (* TRUE : indenté *)

On construit avec les littéraux du dialecte ([..], ['clé' := ..]) : pas de nouvelle syntaxe. JSON_ECRIRE accepte aussi une structure IHM, un TUPLE, un nombre, un texte.

IF JSON_TYPE(Config['seuils']) = JSON_Objet THEN
    Seuil_Haut := JSON_NOMBRE(Config['seuils']['haut'], 9.5);   (* 9.5 si absent *)
END_IF;
SI_PAS_LA := JSON_A(Config, 'version');   (* la clé existe-t-elle ? BOOL *)
Generer — rien a signaler

JSON_TYPE rend une énumération native (JSON_Objet, JSON_Liste, JSON_Texte, JSON_Nombre, JSON_Bool, JSON_Nul, JSON_Absent). Une clé absente rend la valeur JSON_Absent ; un accesseur avec défaut la remplace sans lever d'erreur.

VAR Trame : STRING := 'PRES=7.5bar;DEBIT=12.3'; END_VAR
IF REGEX_TESTE(Trame, 'PRES=([0-9.]+)bar') THEN
    Pression := TO_REAL(REGEX_TROUVE(Trame, 'PRES=([0-9.]+)bar', 1));  (* groupe 1 *)
END_IF;
Code_Ok := REGEX_TESTE(Code_Barre, '^[0-9]{13}$');   (* EAN-13 complet *)

Grammaire ECMAScript (comme JavaScript). REGEX_TROUVE rend la correspondance entière (groupe 0) ou un groupe capturé ; '' si rien. REGEX_TESTE cherche partout ; ^ et $ pour exiger tout le texte.

Nom := REGEX_REMPLACE(Saisie, '[^A-Za-z0-9_]', '_');   (* remplace tout *)
VAR Lignes : LIST OF STRING; Champs : LIST OF STRING; END_VAR
Lignes := RESOURCE_LINES('consignes.csv');
Champs := REGEX_DECOUPE(Lignes[1], ';');   (* ['Pression haute','9.5','bar','A'] *)
Generer — rien a signaler

REGEX_REMPLACE remplace toutes les occurrences ($1 rappelle un groupe). REGEX_DECOUPE coupe au motif. Se lit aussi dans une fx (lecture seule) : {JSON_TEXTE(JSON_LIRE(RESOURCE_READ('ui.json'))['titre'])}.

TRY
    Params := JSON_LIRE(FILE_READ('parametres.json'));
CATCH e
    IHM_LOG(WARNING, CONCAT('Paramètres illisibles : ', e.Message));
    Params := JSON_LIRE('{}');   (* un objet vide, on repart proprement *)
END_TRY;
Generer — rien a signaler

JSON_LIRE sur un texte mal formé, ou un accès de mauvais type sans défaut, lève une erreur claire et catchable (e.Code = 'E_JSON', e.Message cite la position). REGEX_VALIDE(motif) teste un motif saisi avant de l'employer.

Ce qui se passe

  • Un nouveau type ANY (valeur dynamique / JSON), ajouté au modèle comme TypeDesc::Kind::Any. C'est un joker de compilation : une case ANY porte à l'exécution un Obj de son vrai type (STRING, LREAL, BOOL, LIST OF ANY, MAP[STRING] OF ANY, ou nul). Il ne sert QUE dans le dialecte IHM (hmiDialect), jamais dans le ST de l'automate, exactement comme LIST/MAP aujourd'hui.
  • JSON_LIRE(texte) : un objet JSON -> MAP[STRING] OF ANY (clés rangées, comme une MAP STRING) ; un tableau -> LIST OF ANY ; un nombre -> LINT s'il tient en entier sans point ni exposant, sinon LREAL ; une chaîne -> STRING (UTF-8, échappements \n \uXXXX décodés) ; true/false -> BOOL ; null -> une valeur JSON_Nul.
  • JSON_ECRIRE(valeur [, indenté]) : STRING. Prend une valeur ANY, une MAP/LIST/SET/ARRAY/VECTOR, un TUPLE, une structure IHM (ses membres publics, PAS son opérateur TO_STRING), ou un scalaire. INDENTÉ à TRUE : deux espaces par niveau ; sinon compact. Un REAL/LREAL non fini (INF, NAN) et une référence/un rappel sont refusés avec un message clair (le JSON ne les connaît pas).
  • Accès : v['clé'] sur un objet, v[i] sur un tableau, v.Count sur un tableau — comme MAP et LIST. Le type statique du résultat est ANY ; l'emploi concret est vérifié à l'exécution. Une clé absente rend JSON_Absent (pas d'erreur) ; v[i] hors du tableau lève une erreur (comme une liste).
  • Accesseurs sûrs, sur le modèle de MAP_GET/LIST_GET : JSON_NOMBRE(v [, défaut]) : REAL, JSON_ENTIER(v [, défaut]) : DINT, JSON_TEXTE(v [, défaut]) : STRING, JSON_BOOL(v [, défaut]) : BOOL. Avec défaut : rendu si la valeur manque ou n'est pas du bon genre. Sans défaut : une erreur claire et catchable (« la valeur JSON est un texte, pas un nombre »).
  • Interrogation : JSON_TYPE(v) -> énumération native JSON_Type (JSON_Objet, JSON_Liste, JSON_Texte, JSON_Nombre, JSON_Bool, JSON_Nul, JSON_Absent) ; JSON_A(v, clé) : BOOL ; JSON_EST_NUL(v) : BOOL ; JSON_CLES(v) : LIST OF STRING (les clés d'un objet). Construction mutable : JSON_OBJET() et JSON_LISTE() rendent un conteneur ANY vide que MAP_SET/LIST_ADD remplissent.
  • Conversion ANY -> type concret : à une affectation (Pression := v['p']) ou comme argument typé, le moteur convertit avec contrôle, comme un DYNAMIC_CAST : ok si le genre correspond (nombre->REAL/INT, texte->STRING, bool->BOOL), sinon une erreur runtime catchable. Un objet/tableau JSON ne s'affecte qu'à une case ANY, LIST OF ANY ou MAP[STRING] OF ANY de même forme.
  • REGEX_TESTE(texte, motif) : BOOL (cherche partout) ; REGEX_TROUVE(texte, motif [, groupe]) : STRING (groupe 0 = tout ; '' si rien) ; REGEX_TROUVE_TOUT(texte, motif) : LIST OF STRING ; REGEX_GROUPES(texte, motif) : LIST OF STRING (les groupes capturés de la 1re correspondance) ; REGEX_REMPLACE(texte, motif, remplacement) : STRING (tout, $1..$9 rappellent les groupes) ; REGEX_DECOUPE(texte, motif) : LIST OF STRING ; REGEX_VALIDE(motif) : BOOL.
  • Grammaire std::regex ECMAScript, sensible à la casse par défaut (un drapeau 'i' en préfixe '(?i)' n'existe pas en ECMAScript — on documente d'employer des classes). \w \d \s travaillent sur les octets UTF-8 : pour les lettres accentuées (Hélium), écrire des classes explicites. Un motif de littéral invalide est signalé par Compiler/Générer à sa position ; un motif dynamique invalide lève une erreur (ou REGEX_VALIDE le teste avant).
  • Erreurs alignées sur le lot « lever ses erreurs » : code stable (E_JSON, E_REGEX, E_JSON_TYPE) + message cité (position, genre attendu). Un échec en fx (expression d'une propriété) ne casse pas l'affichage : la valeur par défaut est rendue et la Console le dit une fois. Les natives JSON_/REGEX_ sont pures (pas d'effet, pas d'I/O) : utilisables en fx en lecture seule et faciles à couvrir par le lot tests.
  • Chemin d'un fichier : aucune nouvelle I/O. On lit le texte avec les natives existantes FILE_READ / RESOURCE_READ / RESOURCE_LINES (donnees/ du projet) puis JSON_LIRE. Sur la page web WebAssembly, la lecture disque reste bloquée comme les autres natives de fichiers, mais RESOURCE_READ (ressources embarquées) marche : le JSON et le regex eux-mêmes tournent intégralement en WASM (CPU seul).

Chaque fiche a sa signature, son résumé, son exemple avec valeur, et les équivalents C / C++ (comme les autres natives).

La ligne « Résultat final » affiche ANY ; l'aperçu explique qu'une case ANY accepte tout et se lit avec les JSON_.

▤  Les bibliothèques et les espaces de noms tres gros

Range tes types et tes fonctions sous un préfixe (Gaz., Util.) pour qu'ils n'entrent jamais en collision, et partage du code entre projets par une bibliothèque reliée, pas recopiée - avec un nom, une version, et une mise à jour qui te prévient avant de casser.

// Script general. Gaz et Util sont deux espaces declares (projet ou bibliotheque).
VAR_TEMP
    v   : Gaz.T_Vanne;        // un type de l'espace Gaz
    moy : REAL;
END_VAR
v.Position := 50;
moy := Util.Moyenne(PressionA, PressionB);   // une fonction de l'espace Util
IF Gaz.EnDefaut(v) THEN                        // Gaz.EnDefaut : fonction de Gaz
    IHM_JOURNAL('Vanne en defaut');
END_IF;
Generer — rien a signaler

Le prefixe suffit : aucun USING n'est obligatoire. Le premier segment (Gaz, Util) est un espace DECLARE, donc Gaz.T_Vanne est un seul nom qualifie, pas un acces membre.

USING Gaz;
USING Util;
// Ici, les noms de Gaz et de Util s'ecrivent sans prefixe.
VAR_TEMP v : T_Vanne; END_VAR      // T_Vanne = Gaz.T_Vanne
v.Position := Borne(Consigne, 0.0, 100.0);   // Borne = Util.Borne
// Si Gaz ET Util definissaient Borne, l'appel nu serait refuse : "ambigu entre
// Gaz.Borne et Util.Borne - qualifie-le".
Generer — des refus a leur ligne (vois les commentaires REFUSÉ dans le code)

USING est une directive de tete, consommee a la compilation (le rewrite qualifie les noms et retire la ligne). L'interpreteur partage avec API Studio ne voit jamais USING ni d'espace de noms.

VAR_TEMP p : Gaz.T_Pompe; END_VAR
p.Demarrer();              // p est une variable -> methode de Gaz.T_Pompe (lot J1)
Gaz.EnDefaut(p);           // Gaz est un espace declare -> fonction de l'espace
Seuil := Vue_Four.Seuil_Haut;   // Vue_Four est une vue -> membre de vue (existant)
// Un conflit est refuse par Generer : si une variable s'appelait "Gaz",
// "le nom Gaz est a la fois un espace de noms et une variable".
Generer — des refus a leur ligne (vois les commentaires REFUSÉ dans le code)

A.B se lit dans cet ordre : A est-il un espace declare (le plus long chemin d'abord) ? sinon une vue ? sinon une variable (acces membre / methode). Les espaces etant un ensemble ferme et connu, il n'y a pas d'ambiguite.

// Type IHM T_Vanne, champ "Espace de noms" = Gaz. Son nom complet devient Gaz.T_Vanne.
// Fonction Convertir, espace = Gaz, retour REAL : dans Gaz, ses voisins s'ecrivent nus.
FUNCTION Convertir : REAL
VAR_INPUT mbar : REAL; END_VAR
    Convertir := mbar * COEF_BAR;   // COEF_BAR : une constante de l'espace Gaz, nue
END_FUNCTION
Generer — rien a signaler

Un item (type, fonction, script) connait d'office les noms de SON espace sans prefixe (USING implicite de soi-meme). Le champ Espace de noms est une liste des espaces existants + "Nouveau...".

bibliotheque nom="Gaz" version="1.4.0" compat="1.2.0" chemin="libs/Gaz-1.4.0.xpgbib"
// version : celle resolue/reliee sur disque ; compat : le plancher demande (1.x, >=1.2.0).
// Puis le cache de l'interface, pour verifier meme si le fichier manque :
bib_type   nom="T_Vanne" membres="Position:REAL,Defaut:BOOL"
bib_fonction nom="EnDefaut" signature="(v : T_Vanne) : BOOL"
Generer — rien a signaler

Le CODE de la bibliotheque n'est PAS recopie dans le projet (contrairement a un paquet .xpgsymboles) : seuls cette reference et un cache de signatures voyagent. Le projet reste lisible en diff et portable en git.

// A l'ouverture, hmi::biblio compare le fichier trouve au "compat" demande (1.2.0, majeur 1) :
//  Gaz 1.4.0 trouve  -> relie. Note : "Gaz : 1.2.0 -> 1.4.0 (compatible)". Mettre a jour fige 1.4.0.
//  Gaz 1.1.0 trouve  -> averti : "plus ancienne que demandee (1.2.0)" ; un symbole recent manquera.
//  Gaz 2.0.0 trouve  -> REFUSE : "incompatible (2.0.0, le projet demande la 1.x)".
//  Gaz introuvable   -> erreur Generer + "Localiser..." ; le cache garde l'interface pour verifier.
x := Util.Max(3, 7);   // J7 : une bibliotheque publie aussi des fonctions generiques Util.Max<T>
Generer — des refus a leur ligne (vois les commentaires REFUSÉ dans le code)

Compatibilite par semver : meme MAJEUR, mineur >= celui demande. Meme refus que les paquets (core::ErrorCode, pkg::tooNew) pour "vient d'une version plus recente".

Ce qui se passe

  • UN ESPACE DE NOMS EST UN PREFIXE DE NOM, PAS UN CONTENEUR. Un champ 'ns' (Espace de noms) s'ajoute a HmiType, HmiFunction et Script ; le nom complet est ns.nom (Gaz.T_Vanne, Util.Moyenne). Tout le code reste GLOBAL en marche : la resolution est un rewrite a la compilation (comme viewmembers::qualify) qui remplace un nom court par son nom global unique ; le moteur sim:: ne voit que des noms plats. Rien de nouveau n'atteint l'interpreteur.
  • LA PORTEE. Dans son propre espace, un item nomme ses voisins sans prefixe (USING implicite de soi). Ailleurs, on ecrit ns.nom, ou on met 'USING ns;' en tete du corps pour les ecrire nus. USING est une directive de compilation : le rewrite l'applique puis la retire ; une locale ou un parametre de meme nom passe avant un nom importe (le meme 'hidden' que qualify).
  • LA REGLE DE RESOLUTION de A.B (greedy, chemin le plus long d'abord) : 1) A (ou A.B.) est-il un espace declare et nomme-t-il un type/une fonction ? -> reference qualifiee ; 2) sinon A est-il une vue ? -> membre de vue (Vue.Nom, existant) ; 3) sinon A est une variable/parametre/locale -> acces membre ou methode (lot J1). L'ensemble des espaces etant ferme (gathere a la compilation), aucune ambiguite avec l'acces membre Four1.Temperature.
  • CE QUI EST DECLARE. L'ensemble des espaces = l'union des 'ns' des items + le nom des bibliotheques reliees. Un espace vide se garde comme un dossier vide (Project::listFolders, cle 'espaces'). Un nom d'espace est RESERVE : Generer refuse une variable/vue/type qui porte le nom d'un espace, et deux espaces identiques.
  • AMBIGUITE SOUS USING : deux espaces importes qui definissent le meme nom -> l'emploi nu est refuse ("ambigu entre Gaz.Max et Util.Max - qualifie-le"), a sa ligne, avec le clic-correction qui insere le prefixe.
  • UNE BIBLIOTHEQUE EST DU CODE PARTAGE, RELIE ET NON COPIE. Elle a un NOM (son espace de noms de tete : Gaz publie Gaz.T_Vanne...), une VERSION semver, et un contenu (types, fonctions, scripts, avec leurs sous-espaces). Elle vit dans un FICHIER .xpgbib (un zip, comme .xpgtypes : manifeste nom/version/dependances + un petit projet ecrit par serializeProject). Elle se publie depuis un projet (IHM > Bibliotheque > Publier...), ou s'edite comme un projet bibliotheque.
  • LE LIEN, PAS LE CONTENU. Le projet enregistre une ligne 'bibliotheque nom= version= compat= chemin=' + un cache compact de l'interface (bib_type, bib_fonction : noms, membres, signatures, unites). Le code de la bibliotheque n'est jamais recopie dans ihm/ (difference nette avec HmiPackage qui, lui, copie). Un diff de projet reste court ; deux projets partagent reellement le meme code.
  • OU ELLE VIT, COMMENT ON LA TROUVE. Le chemin est cherche relatif au projet d'abord (libs/Gaz-1.4.0.xpgbib : portable en git), puis dans un dossier de bibliotheques partagees de la machine, puis en absolu. Deplacee : 'Localiser...'. Reliee, elle est LECTURE SEULE dans l'editeur (ses types et ses fonctions s'emploient mais ne s'editent pas ; 'Ouvrir la definition' ouvre en lecture seule).
  • VERSION ET COMPATIBILITE (semver, meme majeur, mineur >= demande). Plus recente compatible (1.2 demande, 1.4 trouve) : reliee, note de mise a jour, 'Mettre a jour' fige la version resolue. Plus ancienne (1.1 trouve) : averti, un symbole recent employe devient inconnu. Majeur different (2.0 trouve) : refusee, et le cache d'interface garde le projet verifiable. Absente : erreur + Localiser. Le refus reutilise le code et le message des paquets (pkg::tooNew).
  • METTRE A JOUR, SANS SURPRISE. 'Mettre a jour la bibliotheque' relit le fichier et montre un DIFF de l'interface (symboles ajoutes, retires, signatures changees) ; si un symbole employe a disparu ou change, il liste les ruptures AVANT d'appliquer, chacune a son endroit (comme un plan d'import).
  • LE REGISTRE DES TYPES l'integre. Un type de projet garde sa cle stable 'ihm:615' (l'espace n'est qu'un affichage) ; un type de bibliotheque recoit une cle a lui 'bib:Gaz.T_Vanne'. Entry gagne un champ 'ns' et une provenance 'Bibliotheque Gaz 1.4.0' ou 'Espace Gaz'. Le selecteur groupe par provenance/espace et propose 'Ouvrir la definition' en lecture seule.
  • COMPATIBILITE D'UN PROJET D'AVANT. Sans espace ni bibliotheque, rien ne change : 'ns' vide, pas de ligne bibliotheque, le projet s'ouvre a l'identique et se reecrit au format <= 28 (la cascade de retro-compatibilite existante). Le format monte a 29 seulement a la premiere utilisation d'un espace ou d'un lien. Une 1.12 refuse un format 29 ("vient d'une version plus recente").
  • COHERENCE AVEC LES AUTRES LOTS. Une bibliotheque transporte tout le 1.13 : des types a methodes/heritage/interfaces (J1), des membres avec unite (J6), des fonctions generiques TEMPLATE<T> (J7). Son .xpgbib se serialise avec le modele FINAL de la 1.13 ; a implementer apres J1/J6/J7. La resolution de A.B (espace vs methode vs vue) est le MEME resolveur de noms que J1 et J7 etendent : un seul endroit (hmi::names), pas trois analyseurs de point paralleles.
