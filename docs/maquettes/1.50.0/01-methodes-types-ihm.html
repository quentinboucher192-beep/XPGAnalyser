Les méthodes des types IHM deviennent des fonctions comme les autres

Ta demande : méthodes dans types IHM, pas pareil que les méthodes dans les symboles, il n'y a pas les onglets paramètres, constantes, locales, tests, uniformiser et proposer maquette. Proposition : une seule fenêtre de création (celle des fonctions du symbole) et les cinq mêmes onglets — Code, Paramètres, Locales, Constantes, Tests — pour une fonction du projet, d'une vue, d'une popup, d'un symbole et pour une méthode de type IHM.

Ce que ça change

1
Une seule fenêtre. « Ajouter une méthode… » ouvre la fenêtre des fonctions (HmiNewFunctionDialog), avec un 5e propriétaire : le type. Le titre dit « Nouvelle méthode du type T_Pompe » ; le bouton reste « Créer ». « Redéfinissable » devient « Virtuelle », comme pour un symbole.
2
Les cinq onglets Code · Paramètres · Locales · Constantes · Tests, les mêmes grilles (le type, l'unité, le mode, le défaut, la documentation, « Choisir un type… »), les mêmes fautes soulignées, le même Ctrl+Z.
3
SELF en tête des paramètres, grisé et verrouillé : on le voit, on ne peut ni le renommer ni le retirer. Une signature d'interface n'a que l'onglet Paramètres.
4
Les tests d'une méthode partent d'une instance d'essai du type (ses membres à leur valeur initiale) : « SELF avant » pose des membres, « Vérifier après » peut lire SELF.EnMarche.
·
Les projets existants : à l'ouverture, la ligne « Consigne : REAL; VAR_IN_OUT Cible : T_Pompe » passe dans l'onglet Paramètres et les VAR du corps dans Locales (le bandeau « Migrer » des fonctions, déjà là). Le fichier garde la même méthode.

Questions pour toi

  1. « METHOD » dans « Elle s'écrira » (comme CODESYS) ou « FUNCTION », comme les fonctions de symbole ?
  2. Les génériques par méthode (Convertir<T>) : utiles, ou ceux du type suffisent ?
  3. Une méthode privée : la cacher de l'aide à la saisie hors du type, ou la montrer grisée ?
