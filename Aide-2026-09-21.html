ST_ALM_Cmd

DDT · Alarms · version 1.00 · ST_ALM_Cmd.ddt

Les commandes du gestionnaire d'alarmes. Toutes sont prises SUR FRONT MONTANT.

Utilisation

Sur front, et pas sur niveau : un bouton d'IHM reste a TRUE tant que l'operateur a le doigt dessus. Sur niveau, un acquittement se rejouerait a chaque cycle et acquitterait aussi tout ce qui apparait pendant ce temps.

Une commande refusee ne fait pas de bruit : elle ecrit la raison dans Stat.LastError, qui est vide au debut de chaque cycle. Lisez-le juste apres avoir pose la commande, pas trois cycles plus tard.

Exemple

(* acquitter une alarme designee depuis l'IHM *)
AlmCmd.AckUuid := UDINT_TO_UDINT(%MD1200);
AlmCmd.Ack     := %MX40;

Utilisation

C'est la raison pour laquelle l'UUID n'a besoin d'AUCUNE table : la provenance est dans le nombre. Un journal exporte en CSV reste exploitable des annees apres, sans le projet qui l'a produit.

La disposition des bits :

Un gestionnaire d'alarmes pour 64 alarmes et 256 evenements d'historique. Une instance par groupe.

Utilisation

COMMENT UNE ALARME ARRIVE ICI : par le tableau State, indice par indice, comme les cartes d'E/S le font pour leurs voies. Une ligne par alarme, ecrite une fois. C'est explicite, ca se cherche avec un Ctrl+F, et la macro LierAlarmes l'ecrit toute seule depuis le classeur.

L'ORDRE DANS LE CYCLE. Le gestionnaire lit State ; il faut donc que State soit deja ecrit quand il tourne. Appelez-le APRES vos blocs d'equipement et de voies, et avant les reports vers l'IHM.

L'HISTORIQUE EST UN ANNEAU. Quand il est plein, le plus ancien est perdu - un automate n'alloue pas. Stat.Wrapped le dit, et Seq ne recule jamais : c'est ce qui distingue un historique reboucle d'un historique a trous.

(* declarer, une fois *)

AlmCmd.RegLabel := 'Fuite gaz armoire A';
AlmCmd.RegSev := 4;
AlmCmd.Register := TRUE;   (* front montant *)

(* alimenter, a chaque cycle *)
AlmState[0] := CarteDI_R0S4[2].Val;
AlmState[1] := CarteAI_R0S10[3].Thr[0].Raised;

ALM_Station(Count := 64, CycleMs := 20, Cmd := AlmCmd,
State := AlmState, Defs := AlmDefs,
History := AlmHist, Stat := AlmStat);

DFB_ITL_MATRIX

DFB · Control · version 1.01 · DFB_ITL_MATRIX.dfb

Interverrouillage de 16 vannes par matrice : interdits et prerequis.

Utilisation

DEUX RELATIONS, et les confondre est l'erreur classique :

Forbid[i*16+j] i ne doit PAS etre ouverte pendant que j l'est.

Melange de produits, court-circuit hydraulique.

Require[i*16+j] i ne peut s'ouvrir QUE SI j est ouverte. Une vanne d'aspiration avant une pompe, un event avant un remplissage.

Un interverrouillage qui n'a que le premier laisse ouvrir une vanne dans le vide ; un qui n'a que le second laisse melanger deux produits.

LA MATRICE EST A PLAT : ARRAY[0..255] indice par i*16+j, et non un tableau a deux dimensions. Le format d'echange les ecrit, mais tout ce qui les relit ne les comprend pas encore.

IL NE COMMANDE RIEN. Il dit Allowed[i], et pourquoi non. La vanne reste maitresse de ce qu'elle fait de cette reponse - un bloc qui forcerait la fermeture ferait deux choses au meme endroit.

Exemple

(* 0 interdite pendant que 1 est ouverte *)
MatForbid[0 * 16 + 1] := TRUE;
(* 2 ne s'ouvre que si l'aspiration 5 est ouverte *)
MatRequire[2 * 16 + 5] := TRUE;

ITL_Melange(Count := 8, Open := VannesOuvertes,
Forbid := MatForbid, Require := MatRequire,
Allowed := VannesOk, BlockedBy := VannesPar,
Reason := VannesRaison, Violation := VannesViol);
Vannes[0].OpenReq := Demande[0] AND VannesOk[0];

L'etat REEL de chaque vanne, a cabler sur sa position - pas sur sa commande. Une vanne commandee ouverte mais bloquee fermee ne protege personne.

DFB_MODE_MANAGER

DFB · Control · version 1.01 · DFB_MODE_MANAGER.dfb

Choisit le mode actif parmi 16 : priorite, temps minimum, repli.

Utilisation

CE QU'IL FAIT ET CE QU'IL NE FAIT PAS. Il decide QUEL mode tourne ;

il n'appelle rien. Ce qui s'execute dans chaque mode est une suite de sous-routines, dans un ordre - et une suite de noms dans un ordre ne se range pas dans un DDT. C'est du CODE, et c'est la macro GenererModes qui l'ecrit, sous forme d'un CASE.

Separer les deux n'est pas une commodite : la condition d'entree d'un mode se calcule dans votre programme et arrive par Def[i].Req, alors que l'ordre des appels est fige a la generation.

UN MODE PRIORITAIRE PASSE MALGRE LE TEMPS MINIMUM, des que sa priorite atteint ForcePriority. Un arret d'urgence qui attend la fin d'un temps de sejour n'est pas un arret d'urgence.

Exemple

(* les conditions, calculees par vous *)
Modes[0].Req := NOT Defaut AND NOT Manu;        (* automatique *)
Modes[1].Req := Manu;                            (* manuel *)
Modes[2].Req := Defaut;                          (* repli *)

MODE_Station(Count := 3, CycleMs := 20, FallbackMode := 0,
ForcePriority := 100, Def := Modes,
Current := ModeCourant, PrevMode := ModePrecedent,
CurrentMs := ModeDepuisMs);

Dix pompes, deux en marche, on bascule toutes les X minutes : c'est le cas pour lequel ce bloc existe. IL NE COMMANDE RIEN - il dit lesquels doivent tourner, et le bloc d'equipement fait le reste.

TROIS MANIERES DE CHOISIR, et le choix compte :

0 ordre fixe les premiers disponibles, toujours dans le meme ordre. Previsible, et use toujours les memes.

1 carrousel on decale d'un cran a chaque rotation. Simple, et l'usure se repartit meme si personne ne mesure rien.

2 moins usee celle qui a le moins d'heures part en premier.

C'est ce qu'on veut vraiment, et ca demande que RunMs soit tenu a jour.

LA ROTATION AVANCE MEME QUAND RIEN NE TOURNE. Sinon une installation a l'arret repartirait toujours sur la meme machine.

Exemple

ROT_Gavage(Count := 3, Demand := 2, Mode := 2,
RotateMs := 3600000,    (* une heure *)
CycleMs := 20, Mem := Pompes_Rot);

(* cabler, dans les deux sens *)
Pompes_Rot[0].Available := Pompes[0].Ready;
Pompes_Rot[0].RunMs     := Pompes[0].RunMs;
Pompes[0].ManRunReq     := Pompes_Rot[0].RunReq;

ST_IO_Thr

DDT · IO · version 1.00 · ST_IO_Thr.ddt

Un seuil d'alarme. Quatre de ceux-la vivent dans chaque voie analogique.

Utilisation

Un seuil dit une chose : "la valeur est du mauvais cote de Val, et elle y est depuis assez longtemps". Les quatre reglages qui suivent servent tous a rendre cette phrase utilisable sur une mesure reelle, qui bruite et qui oscille autour du seuil.

L'HYSTERESIS JOUE A LA RETOMBEE SEULEMENT. Un seuil haut a 80 avec Hyst = 2 se leve a 80 et retombe a 78. L'appliquer des deux cotes ferait dire au seuil un nombre different selon le cote par lequel on l'approche, et 80 ne voudrait plus rien dire.

LE RETARD EST UN TEMPS DE MAINTIEN, PAS UNE TEMPORISATION D'ALARME. Le compteur repart a zero des que la condition tombe, meme une seule scrutation. C'est ce qui filtre une pointe de mesure, et c'est aussi pourquoi un signal qui oscille autour du seuil ne leve jamais l'alarme.

Les quatre seuils d'une voie sont INDEPENDANTS et sans ordre : rien n'empeche Thr[0] d'etre un seuil bas et Thr[3] un seuil tres haut. La convention est a vous ; le bloc ne la connait pas.

EnBOOLMemberTRUE to evaluate this threshold at all
FALSE laisse le seuil tranquille : il ne se leve pas, et ses sorties sont remises a zero a chaque scrutation.
C'est aussi ce qui se passe quand la voie est en defaut d'echelle. Un seuil evalue sur une mesure qu'on ne sait pas convertir ne dit rien de vrai.
DirINTMember0 = raises when the value goes ABOVE Val, 1 = below
0 : le seuil se leve quand la valeur passe AU-DESSUS de Val. 1 : quand elle passe EN DESSOUS.
Il n'y a pas de troisieme possibilite. Une bande - "en dehors de 10..90" - s'ecrit avec deux seuils, un dans chaque sens.
ValREALMemberthe threshold, in engineering units
Le seuil, en UNITES PHYSIQUES, pas en points de carte. Il se compare a Val de la voie, c'est-a-dire apres echelle, bande morte et filtre.
HystREALMemberrelease band: applied on the way OUT, never on the way in
La bande de retombee, dans les memes unites. 0 la desactive : le seuil retombe exactement ou il s'est leve, ce qui fait battre une mesure bruitee.
Une valeur de l'ordre du bruit de la mesure suffit. Trop grande, elle retarde la retombee d'une alarme qui a reellement disparu.
DelayMsDINTMemberhow long the condition must hold before it is an alarm
Combien de temps la condition doit tenir avant que ce soit une alarme. 0 leve des la premiere scrutation ou la condition est vraie.
Le temps s'accumule a partir de CycleMs : une periode de tache fausse fausse tous les retards de tous les seuils, sans qu'aucune erreur ne le signale.

1 information, 2 avertissement, 3 defaut, 4 la machine doit s'arreter.

Utilisation

La section se lit en deux moities, et la separation est le coeur de l'affaire. DFB_MODE_MANAGER decide QUEL mode est actif : c'est de la donnee - une condition, une priorite, un temps minimum - et ca vit dans un DDT.

CETTE SECTION decide CE QUI TOURNE dans chaque mode : c'est une suite de noms de sous-routines dans un ORDRE, et une suite ordonnee de noms ne se range pas dans un DDT. C'est du code, et il faut donc l'ecrire.

RELANCEE, ELLE REECRIT LA SECTION ENTIERE plutot que d'y ajouter. Une section de modes a moitie ancienne et a moitie nouvelle est pire que les deux. Ce qui a ete ajoute a la main dans cette section sera perdu.

MACRO · Macros · ImporterAlarmes.mac

Enregistre les alarmes de voie dans DFB_ALM_MANAGER : UUID, libelle, gravite, et la remontee d'etat a chaque cycle.

Utilisation

Depuis l'onglet ES.

POURQUOI ELLE EXISTE A COTE DE ImporterReports. Les deux parlent d'alarmes et ne parlent pas des memes. ImporterReports recopie vers l'IHM les defauts d'EQUIPEMENT lus dans l'onglet Liens. Celle-ci enregistre les alarmes de VOIE : une entree TOR dont AlarmEn est coche, un seuil analogique actif. Elles ne viennent pas du meme onglet et ne passent pas par le meme chemin.

L'UUID PORTE LA PROVENANCE. Il n'est pas tire au hasard : ses 32 bits sont le rack, le module, la voie et le numero de seuil, packes. Un identifiant trouve dans un journal dans cinq ans dit encore de quelle voie il vient, sans aucune table a tenir a jour. bits 31..28 genre (1 TOR, 2 seuil analogique), 27..24 rack, 23..18 module, 17..12 voie, 11..8 seuil.

La macro ecrit un LITTERAL plutot que d'appeler AlmUuid, pour que le fichier genere se lise sans rien executer. Le commentaire pose a cote de chaque UUID en donne les parties, ce qui rend un ecart visible plutot que silencieux.

LES QUATRE FAMILLES EN UNE EXECUTION, contrairement a l'ancienne LierAlarmes qui travaillait sur un export CSV d'un seul onglet.

LE REGISTRE COMPTE 64 EMPLACEMENTS. Au-dela, les alarmes suivantes ne sont pas enregistrees et un avertissement le dit.

LA SECTION EST REECRITE ENTIEREMENT a chaque execution. Ce qui y a ete ajoute a la main est perdu. C'est voulu : une section a moitie ancienne et a moitie nouvelle est pire que les deux, et on ne peut pas deviner ce qui a ete ajoute expres.

ELLE NE FAIT QU'UNE ETAPE, et elle suppose que les precedentes ont tourne. Pour generer tout le programme en une fois - types, blocs, variables, instances, E/S, equipements, cablage, reports et alarmes - c'est ImporterProgramme.

ImporterReports

MACRO · Macros · ImporterReports.mac

Ecrit les echanges avec l'IHM : commandes en tete de tache, mesures et recopie des alarmes en queue. Elle n'enregistre rien dans le gestionnaire d'alarmes.

Utilisation

Depuis l'onglet Liens. Trois types, et leur place dans la tache est le sujet :

TC, commande : l'IHM ecrit, l'automate lit. EN PREMIER. Une TC lue en fin de tache fait travailler tout le programme sur la commande du cycle precedent - un bouton d'IHM qui repond avec un cycle de retard.

TM, mesure, et TA, alarme : l'automate ecrit, l'IHM lit. EN DERNIER. Une TM ecrite en tete publie la valeur d'avant que le programme n'ait tourne.

Aucun des deux ne se voit sur une temperature. Les deux se voient sur un comptage de pieces.

LA CONVERSION DE TYPE VIENT DU CATALOGUE. Un %MW est un INT ; Pressure est un REAL et FbkMs un DINT. Ecrire l'affectation sans conversion donne un projet qui ne compile pas, et deviner le type d'apres le nom donne un projet qui compile et qui ment. Le type est dans l'onglet Catalogue, on l'y lit - et quand il est introuvable, la ligne est ecrite avec un commentaire qui le dit plutot qu'avec une conversion inventee.

ELLE N'ENREGISTRE AUCUNE ALARME DANS LE GESTIONNAIRE. Une ligne TA est recopiee vers son bit de %MW, et rien de plus : le defaut s'affiche sur l'IHM mais il ne se date pas, ne s'acquitte pas, n'entre pas dans l'historique et ne se compte pas. Le registre est unique - 64 emplacements pour tout le projet - et deux macros ne peuvent pas se partager un compteur d'emplacements. C'est ImporterProgramme qui pose les alarmes de voie ET celles d'equipement, parce qu'elle est seule a les voir toutes.

ELLE SUPPOSE QUE LES EQUIPEMENTS EXISTENT DEJA. Lancee seule sur un projet vide, elle ecrit des lignes qui citent des variables qui n'existent pas : c'est ImporterEquipements qui les declare, ou ImporterProgramme qui fait tout.

LA SECTION EST REECRITE ENTIEREMENT a chaque execution. Ce qui y a ete ajoute a la main est perdu. C'est voulu : une section a moitie ancienne et a moitie nouvelle est pire que les deux, et on ne peut pas deviner ce qui a ete ajoute expres.

Ecrit les deux sections de mapping : le cablage de chaque voie, tous ses reglages, et l'appel du bloc de sa carte.

Utilisation

ERREURXPG-0101

Ce dossier n'est pas un projet

Pourquoi

Le dossier ne contient pas de project.xpgproj. C'est ce fichier, et lui seul, qui fait d'un dossier un projet : il porte le nom de l'affaire, l'automate et l'etat (DEV, FINISH, LOCK).

Ce que ca change

Rien n'est ouvert. Les exports qui se trouvent dans le dossier ne sont pas lus tout seuls : un .XPG posé a cote d'autres fichiers reste un fichier.

Quoi faire

  1. Ouvrez le .XPG directement plutot que son dossier : l'application cree alors un projet autour.
  2. Si le projet existait et que project.xpgproj a disparu, recreez un projet et reimportez l'export : le reste du dossier est du cache, il se reconstruit.
  3. Verifiez que vous n'avez pas designe le dossier PARENT du projet.

ALERTEXPG-0102

La configuration materielle n'est pas dans un .XPG

Pourquoi

Un export .XPG contient le programme : types, variables, sections, taches. Le rack, les modules et leurs references vivent dans un .XHW, qui est un export separe de Control Expert.

Ce que ca change

Le projet s'ouvre et tout le programme est la, mais la vue Rack est vide et les adresses %I/%Q ne peuvent pas etre rattachees a un module. L'analyse des E/S est donc partielle, et elle le dit plutot que de deviner un rack.

Quoi faire

  1. Exportez aussi le .XHW depuis Control Expert et ouvrez-le : il complete le projet deja charge au lieu de le remplacer.
  2. Les deux fichiers peuvent etre donnes ensemble, separes par un point-virgule, dans le champ de chemin de l'accueil.

Un type declare n'est defini nulle part

Une variable utilise un type que l'export ne definit pas : un DDT d'une bibliotheque non exportee, ou un bloc d'une famille absente.

ALERTEXPG-1301

Deux variables a la meme adresse

Pourquoi

Deux declarations pointent sur le meme %MW, %M ou la meme voie. Control Expert l'accepte : c'est parfois voulu (une vue en mot d'un groupe de bits), et le plus souvent une adresse recopiee sans etre changee.

Ce que ca change

Les deux variables sont le MEME emplacement memoire. Ecrire l'une ecrase l'autre, et le programme se comporte correctement jusqu'au jour ou les deux sont ecrites dans le meme cycle.

Quoi faire

  1. Regardez si l'une des deux est un alias volontaire ; si oui, elle merite un commentaire qui le dit, sans quoi la question se reposera.
  2. Sinon, la deuxieme adresse a ete oubliee lors d'un copier-coller : renumerotez-la dans la zone libre indiquee par le classeur.

ALERTEXPG-2101

Cette section n'est pas en Structured Text

Pourquoi

Le simulateur execute du ST, et rien d'autre. Une section en LD, FBD, IL ou SFC est lue, comptee, affichee - mais pas executee.

Ce que ca change

Elle est SAUTEE pendant la simulation. Les variables qu'elle ecrirait gardent leur valeur, ce qui peut faire croire qu'un equipement ne demarre pas alors que c'est la section de commande qui n'a pas tourne.

Quoi faire

  1. Regardez la liste de l'ordre d'execution : les sections non simulees y sont marquees en orange, donc on sait ce qui manque avant de s'interroger.
  2. Pour verifier une logique LD, forcez a la main les variables qu'elle aurait ecrites et relancez le cycle.
  3. Une section de mapping E/S generee par les macros est toujours en ST : si celle-ci ne l'est pas, elle a ete ecrite a la main.

ERREURXPG-2201

Une boucle ne se termine pas

Pourquoi

Une boucle FOR, WHILE ou REPEAT a depasse son budget d'iterations. Le simulateur en fixe un parce qu'un automate, lui, a un chien de garde : une boucle sans fin n'y tourne pas non plus, elle provoque un defaut de tache.

Ce que ca change

LE CYCLE EST ARRETE. Le programme n'a pas fini son balayage, donc l'etat affiche est celui d'un cycle incomplet : les sections qui suivaient n'ont pas tourne du tout.

Quoi faire

  1. Regardez la condition de sortie : une comparaison sur un REAL qui n'atteint jamais exactement sa borne est la cause la plus frequente.
  2. Un FOR dont le pas est nul ne se termine jamais ; c'est signale a part.
  3. Un compteur modifie A L'INTERIEUR de la boucle et relu comme borne est le deuxieme cas classique.

Glossaire

Le vocabulaire que personne ne demande.

TC
Une commande venant de la supervision. Elle se lit EN TETE de tache : lue en fin de cycle, elle fait travailler tout le programme sur la commande du cycle precedent, et un bouton repond avec un cycle de retard.
TM
Une valeur publiee vers la supervision. Elle s'ecrit EN QUEUE de tache, apres que le programme l'ait calculee : ecrite en tete, elle publie la valeur du cycle precedent.
TA
Comme une TM, mais c'est un booleen de defaut. Depuis ImporterProgramme, une TA est aussi enregistree dans le registre de DFB_ALM_MANAGER : sans ca elle s'affiche mais ne se date pas, ne s'acquitte pas et n'entre pas dans l'historique.
DDT
Un type compose, declare une fois et instancie autant de fois qu'on veut. ST_EQ_Pump, ST_IO_Dig en sont. Un DDT ne contient QUE des donnees : pas de code, donc pas de temporisateur - c'est pourquoi les blocs recoivent CycleMs.
DFB
Du code avec une memoire. Chaque instance garde son etat d'un cycle sur l'autre, ce qu'une fonction ne fait pas. DFB_EQ_PUMP, DFB_IO_DIG16 en sont.
POU
Une section, une unite de programme, un type de bloc, une sous-routine. Le modele les range tous au meme endroit, et c'est leur genre qui les separe.
EBOOL
Un booleen etendu : en plus de sa valeur, il retient le front montant et le front descendant du cycle. C'est ce qui permet a %M12 de servir de bit de front sans variable supplementaire. Un BOOL ordinaire n'a pas cette memoire.
%MW
Un entier 16 bits, adresse par son numero : %MW1000. C'est le vehicule habituel des reports vers l'IHM. %MW1000:X3 en designe le bit 3.
%M
Un booleen adresse par son numero : %M40. Ecrit %MX40 dans certaines notations. Les zones MW et MX sont declarees dans la configuration de l'automate et l'onglet Config du classeur.
%I
%I0.4.2 : rack 0, module 4, voie 2. Une entree tout ou rien. %IW pour une entree analogique, %Q et %QW pour les sorties.
MAST
La tache cyclique ou periodique qui porte le programme. Control Expert execute ses sections DANS L'ORDRE DU NAVIGATEUR DE PROJET, et cet ordre se pose a la main : creer une section ne la place pas.
watchdog
La duree au-dela de laquelle l'automate declare la tache en defaut et s'arrete. C'est pourquoi une boucle sans fin n'est pas un ralentissement : c'est un arret.
front montant
Un ordre pris sur front s'execute au changement, pas tant que le bit est a TRUE. Les commandes du gestionnaire d'alarmes - Ack, Reset, Register - le sont toutes : sans ca, maintenir le bit acquitterait en boucle.
anti-rebond
DebounceMs sur une voie tout ou rien. A zero, tout passe, ce qui est le cas habituel. Quelques dizaines de millisecondes suffisent a filtrer un contact sec qui grelotte.
hysteresis
Hyst sur un seuil analogique. Le seuil se leve a Val et ne retombe qu'a Val - Hyst : une mesure qui oscille autour de la consigne ne produit donc pas une alarme par seconde.
UUID
32 bits : genre, rack, module, voie, sous-numero, code. Compose par AlmUuid, relu par AlmDecode, et cite par l'IHM. Il ne depend PAS de l'emplacement dans le registre, sans quoi inserer une alarme changerait toutes les vues.
DDT membre
Dans le modele, un membre de DDT est une variable de portee DerivedMember dont le proprietaire est le type. C'est ce qui permet a une meme structure de cinquante champs de ne couter qu'une declaration.
